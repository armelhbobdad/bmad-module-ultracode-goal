# Changelog

All notable changes to this project will be documented in this file. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### ⚠ BREAKING CHANGES

- **The per-story production gate now requires `--nfr` and `--test-review`, and the epic roll-up must declare itself with `--epic-level`.** Under `--profile production`, `scripts/gate_eval.py` used to *skip* an omitted signal in silence: the AND never ran, `nfr_status` / `review_score` rendered `null`, and the verdict was computed without it, so a forgotten flag bought a **higher** verdict than supplying a failing artifact would have. Each omission is now a failing signal, with a reason naming the flag.

  **Who this breaks, and the migration.** The epic-level roll-up, and it was doing the right thing. `references/gate.md` told runs to invoke it as `--profile production` with neither flag, which was correct: TEA writes NFR and test-review per story, so there is no aggregate to AND. That invocation now returns `reloop` instead of `advance`. **Add `--epic-level`.** It declares the omission rather than leaving it inferred from an absent flag, and the two used to be the same input, which is exactly why a forgotten flag on a story gate was indistinguishable from a correct roll-up. It cannot be combined with either path (an invocation error, exit 2), and it is a no-op under `--profile light`. A per-story production gate that already passed both flags is unaffected.

- **The verdict JSON carries a new `epic_level` boolean.** `docs/_internal/STABILITY.md` declares the printed key set as the consumable shape, so a consumer validating it strictly must accept the new key. It exists because the `reasons` wording is explicitly non-contractual, which left no supported way to tell an `advance` that ANDed both production signals from one that skipped them.

- **`--limit` in `scripts/drive_epic.py` counts spawns, not distinct stories.** It always documented itself as capping sessions, and a retry is a paid session, so retries now consume it. The driver is not an enumerated public surface; recorded here for completeness.

### Fixed

- **Gate: an artifact-less story could resolve a NEIGHBOUR's gate and advance on it, by two different routes.** `_resolve_gate_file` scoped resolution to a story's artifacts and then, when the story had a per-story slim gate file but no trace report, left every report in the directory in play and returned the first frontmatter hint it met. Observed handing an unrelated epic's **PASS** back as the story's verdict; a spurious FAIL gets investigated, a spurious PASS is the verdict nobody re-reads. Separately, `_is_per_story_named` (the discriminator that switches fail-closed resolution *on*) asked whether a filename stem's last component is numeric, which is false for every id this module produces once a story is split or slugged: `trace-92-0a` ends in `0a`. A directory full of real per-story artifacts therefore reported itself generic, the fail-closed branch never fired, and `--story 92-7f-never-driven` returned `PASS` from a neighbour's file. The story's own file now wins before any hint is read, and the naming rule is structural rather than lexical.
- **Gate: a markdown file merely NAMED for a story counted as that story's trace report.** `references/gate.md` tells the non-web author to write `nfr-assessment-<id>.md` and `test-review-<id>.md` into the same directory as the trace pair, and both match the id-component test, so a story that produced its NFR and review but never authored its trace pair looked *present* — suppressing the fail-closed return and falling through to the unscoped summary. Resolution now scopes to **declared** trace reports, the predicate the frontmatter-hint loop already applied.
- **Finalize: the gate trail rendered one story's verdict as every sibling's.** `gate_trail.py` keyed its recorded-verdict map by `numeric_prefix`, collapsing every split story of an epic into one bucket named for the bare epic number. Measured against a real 76-story epic: **63 stories carried a `defer` only one of them had reached.** The trail's own header promises that an absent verdict reads `n/a`, which is what made it dangerous — a reader who trusts that promise trusts every cell that is not `n/a`. Verdicts are now keyed verbatim and matched under a uniqueness rule: a heading matching more than one story names none of them. The same truncation rendered `Gate artifact: n/a` for files `gate_eval.py` read from the same directory seconds earlier, and `nfr-assessment-<id>.md` was being selected as the trace report because it sorts first.
- **Execute: a green sweep could mean almost nothing, on three axes at once.** Step 2 reasoned only about package breadth, so a polyglot repo's aggregate task reported every task green while an entire language's suite was never invoked; a coverage ratchet or storybook suite that is a *sibling* task rather than a dependency of `test` sat red across a whole Epic; and in a content-addressed runner the post-commit re-verify replayed the pre-commit answer verbatim, because committing changes a file's git *tracking state* and not one of its bytes. Steps 2 and 5 now require all three axes and a cache-defeating run. Also ruled: a repo-side hook rejection leaves the tests-ran marker matching character for character, so the guard waves the retry through carrying evidence from before the fix; long verification output is captured to a file rather than piped through a filter, because a cold build and a hang look identical through one; and a story that must build a throwaway program has a named scratch directory.
- **Preflight: the guard's Cross-Session Recall invariant was inert in every install.** The invariant gates a claude-mem MCP call, and the guard denies one correctly — but Claude Code only invokes a `PreToolUse` group for the tools its `matcher` selects, and both known installs armed it against `Bash`, which no MCP call matches. The arming assertion checked *presence* only, so it passed. Preflight now pins an all-tools matcher and requires the assertion to check the matcher itself.
- **Ingest: Cross-Session Recall had no branch for the ordinary headless outcome.** The fork was *off* or *tools-unavailable*; the real case is that the tools are listed, their schemas resolve, and the refusal arrives only when the call is made — recorded on 25 consecutive runs of one epic, with different runs latching different values because nobody was told which. The third state is now named, the first denial is final, and a probe may never be synthesised to stand in for a denied call: an empty `[]` satisfies the capability contract and latches **green**, claiming a surface this run never reached.
- **Finalize: a read probe authorised a write, and the drain then destroyed what it was meant to rescue.** The latch is validated by a `get_observations`-shaped probe, and the recall write routed a `save_observation` off it. On a surface exposing the read family and no write tool, the drain replayed every parked payload against nothing, bumping each one closer to the dead-letter file. Absence now has its own branch and its own log line, since `WARN mem-write-deferred` means a call was attempted and failed.
- **Execute: a row too large to drive had no route, and the terminal it produces had no vocabulary.** One epic took the decomposition path seven times and re-derived the reasoning each time. The spine now sizes a row before step 0 writes any marker, and decomposition is a named terminal that writes no baseline and no tests-ran marker. The three conventions it states are properties of `scripts/drive_epic.py` rather than taste: children go **before** the parent row, and the parent is set `done` once they exist, because the driver takes the first not-`done` row in *file* order and otherwise halts on a row no session will advance. An invocation that did durable work and advanced no row emits `blocked` with a sidecar `kind` of `story-decomposed` or `defined-not-driven`, and the driver reports that as a **handoff** rather than a bare halt.
- **A resume routed into Execute no longer looks like a blocked launch.** `formalize_check.py` is epic-scoped by construction (it takes no `--story`), so on a long Epic it reads `blocked` on gaps belonging to stories the invocation is not driving. A conductor applying the launch non-negotiable literally on every resume would block a healthy run forever.
- **Gate: the non-web path named two of the four artifacts it makes the author responsible for, and had no red-phase standard at all.** `--nfr` / `--test-review` take explicit paths, so nothing mechanical caught each story's NFR and review overwriting the previous story's in the shared trace dir. And the section ruled the acceptance-test bar ("un-skipped and passing") while saying nothing about how un-skipped is reached from a red start — on the one path where the generator that normally creates the skips cannot run, so a run that skipped the red phase entirely satisfied every other sentence.
- **The driver survives an in-flight spawn death instead of reporting it as a failure** (behaviour change). A `claude -p` subprocess can be terminated by the API layer mid-run; the child exits non-zero having written no terminal, so `scripts/drive_epic.py` landed on `no-terminal` and stopped the whole drive. Measured over one 22-spawn session: **eleven** such deaths, at 4 / 6 / 14 / 20 / 53 / 80 / 95 / 154 / 175 / 222 turns, with no turn-count pattern, no story pattern, and the same row landing on the next attempt against identical state. There is nothing to detect in advance and nothing to avoid, so an operator was the retry loop eight times and that was the only reason the epic advanced. A `no-terminal` stop is now retried up to `--max-abort-retries` times (default 2, `0` restores the old behaviour), and **only** when the post-stop triage below finds the tree clean and HEAD unmoved. Every other stop keeps its single-shot fail-closed behaviour, because each means something specific that an identical second spawn cannot change. `--limit` counts spawns, retries included: it is the operator's spend bound.
- **A killed spawn now reports the tree it left behind.** The driver stopped, said no advance, and said nothing about the state on disk, so an unattended loop discarded work that was already green and would re-spawn over work in progress. Of one session's `$414`, `$120` sat in spawns reported as failures and `$82` of that survived only because a human triaged it by hand. Every **post-spawn** stop now prints a read-only triage block: clean tree with HEAD advanced (the work committed, only close-out is missing, do not re-drive), clean and unmoved (nothing landed), dirty (may hold an already-green suite), or an unreadable pre-spawn HEAD. It **reports and never decides** - committing another session's unfinished work needs judgment about whether the subject is complete, not merely whether it compiles. It also names any intent-to-add path explicitly, because `git status` renders those with a blank index column (so the obvious `^A ` match misses them) and `git checkout -- <path>` then truncates one to zero bytes and exits `0`; that hazard fired twice for real in a single session. The triage runs `status` and `rev-parse` only, so the driver's read-only property is unchanged, and it excludes the run-artifacts directory from its safety judgment because the driver deletes the pinned terminal file there itself on every lap.
- **Gate: the blocked envelope adapter no longer writes a `blocked` result over a successful run** (potentially breaking). `headless_envelope.build_headless_envelope` is the **blocked** adapter, but its name reads as the adapter for headless generally, and handed a complete-shaped mapping it did not raise: `fr5_blockers` found no blockers in it, the fail-closed branch synthesised a `formalize :: formalize verdict is unreadable or missing` one, and the call then appended that fabrication to `.decision-log.md` **and** wrote a `blocked` `run-result.json` at the pinned path. Both are artifacts an automator and a resume read, and it happened on a run that had completed. The adapter now raises `ValueError` on a mapping carrying `status: "complete"`, before either side effect, and is additionally exported as `build_blocked_envelope` so the name states the shape. `references/finalize.md` and `SKILL.md` name both entry points. Breaking only for a caller that was already corrupting its own terminal artifacts.
- **Gate: an escalated run's envelope can carry the report it actually produced.** `build_headless_envelope` hard-coded `report: null` / `deferred_work: null` with no parameter to supply either, because the blocked shape was written for runs that block *before* Stage 6. An **escalated** run reaches Stage 6 and does produce a run report and a gate trail, so the envelope under-reported what was on disk for the one run most worth reading. Both are now optional keyword arguments, defaulting to `None` so an early block is byte-identical to before. The five-key set and key order are unchanged.
- **Gate: the envelope adapter no longer injects an em-dash into its own output.** `_one_line` joined a blocker's `source` and `decision_needed` with U+2014, so the stdout envelope, the `run-result.json` beside it, and the blocker list appended to `.decision-log.md` all carried a character the caller never supplied. Latent here because `_bmad-output/` is gitignored, but red in any project that tracks its run artifacts and lints them for it. Now a plain `-`; no key, no byte-identity property, and no test that compares the two are affected, since both sinks render from the same string.

## [1.0.1](https://github.com/armelhbobdad/bmad-module-ultracode-goal/compare/v1.0.0...v1.0.1) (2026-07-28)

### Details

- **The knowledge-graph refresh delegated a flag that does nothing** (behaviour change). Finalize shipped `timeout 300 graphify . --update`, and against graphify 0.9.26 the bare `.` falls through to `graphify extract` while `--update` is silently dropped by that subcommand's argument loop, which ends in a bare `else: i += 1`. The step still behaved incrementally, because `extract` gates on the manifest, so nothing looked broken; but the flag naming the mechanism was dead, and `extract` is the path that dispatches semantic extraction, meaning a run whose Epic touched a Markdown file could send that content to whichever LLM backend graphify auto-detects and spend the operator's API budget on the way out of an unattended run. The delegation is now `timeout 300 graphify update .`, the subcommand that re-extracts code files against the existing graph with no LLM call, no API key, and no network request. What the run now refreshes is the graph's parsed layer, which is the source code plus the Markdown family (`.md`, `.mdx`, `.qmd`, `.skill`), so an Epic's new modules and the story files it wrote are both picked up; what it no longer touches is the semantic layer over images, PDFs, and papers, which is the pass that costs money and sends content off the machine. Unknown flags now also fail loudly, since `update` rejects an unrecognised option with a usage error where `extract` ignores it, which is the property whose absence hid the original bug. The precondition moved with the command, from `graphify-out/manifest.json` to the `graphify-out/graph.json` this subcommand actually updates. `SECURITY.md`'s egress disclosure is corrected accordingly: this integration now makes no network call at all.
- **Docs: the optional knowledge-graph refresh shipped in v1.0.0 undocumented.** `graphify_integration` has been a live knob since [5a8da51](https://github.com/armelhbobdad/bmad-module-ultracode-goal/commit/5a8da51e80ad865f450c6410070e1df92152d7e3), implemented at Finalize and pinned by tests, but nothing in `docs/` or `README.md` named it: the only way to discover it was to open the installed `customize.toml` and read a comment, which is the layer the docs tell you *not* to edit. There is now a [Knowledge-Graph Refresh](docs/knowledge-graph-refresh.md) page covering the two preconditions UCG checks (the CLI on `PATH`, an existing `graphify-out/graph.json`), the value space (`off`/`refresh`, not the `on`/`off` that its neighbour `cross_session_recall` takes, which is the natural thing to copy and silently leaves the step off), the difference between a silent absence and a logged failure, and the install-name trap (the PyPI package is `graphifyy`, the command is `graphify`). It also states what no surface stated anywhere: which layer of the graph a refresh actually touches, and that graphify's general extraction path would send documents to an auto-detected LLM backend on your key, which is why the delegation is pinned to the subcommand that cannot (see the entry above). `SECURITY.md` now covers both optional integrations rather than describing only claude-mem. `docs/architecture.md`'s knob enumeration was stale in the same way and now names `on_escalation`, the four `health_check_*` keys, and both optional integrations, and it gives the installed base-layer path (`{project-root}/_bmad/ucg/ultracode-goal/customize.toml`) that the "skill root" phrasing hid from anyone who installed the module rather than cloned it. The comparison page's Extensibility row lists both integrations too, as facts about UCG's surface rather than as a claimed advantage over bmad-loop's plugin system.

## [1.0.0](https://github.com/armelhbobdad/bmad-module-ultracode-goal/compare/v0.5.1...v1.0.0) (2026-07-28)

### Deprecated

- **`story_token_budget`** is deprecated and is now a no-op. The key is still shipped in `customize.toml`, still accepted, and still resolves, so existing team and user overrides keep working and nothing errors; it simply has no effect. Nothing reads it any more: the Stop hook counts turns only, and the preflight stage no longer injects a token budget into the hook environment. The runaway bound is `max_turns_per_story`, enforced by the "stop after N turns" clause in the run condition and by the gate's re-loop budget, with the Stop hook as the advisory recorder. Use `max_turns_per_story` instead.

### Details

- **Cross-Session Recall** (optional): when [claude-mem](https://github.com/thedotmack/claude-mem) is installed and cross_session_recall is set to on, the executor consults prior runs of the same repo during Ingest and Preflight and records one structured outcome at Finalize, advisory only, hook-latched, never part of the gate. No effect when claude-mem is absent. Off by default.
- **The docs link guard is now tested, and no longer blind to root-absolute targets.** `validate-docs-links.js` became a required status check without any tests of its own, which is the wrong order: a bug in it either blocks a legitimate PR or waves a broken link through, and nothing would have said which. Its paths came from `__dirname`, so it could only ever inspect its own repo and could not be driven against a fixture; `--project-root`, `--docs-dir`, and `--build-dir` now override that, `run()` returns its outcome instead of calling `process.exit`, and 23 tests pin the behaviour that was previously hand-verified once: fence and inline-code blanking, base inference from the built artifact, `src`/`srcset` resolution, the page-relative route regression, site-root escapes, and `--require-build` failing independently of `--strict`. The source pass also skipped every root-absolute `.md` target, so `[x](/architecture.md)` was unchecked: GitHub resolves it against the **repository** root while the rewriter treats `docs/` as the site root, so it can be a valid route pointing at a file that does not exist. It now resolves those against the repo root, which is the surface that pass owns.
- **`SECURITY.md` did not say which repository the protected-branch guard reads.** Invariant 1 is scoped to the branch of the directory Claude Code is running in, not the repository the command targets, so a `git commit` aimed at another checkout is denied whenever the session's own repo sits on `main`. That is deliberate and errs toward denying, but the hook-security section described the check without it, which made a refusal in an unrelated repo look like a malfunction. Documented in `SECURITY.md`, `docs/architecture.md`, and the guard's own docstring.
- **Docs site: in-body links now resolve, and a guard stops the class recurring.** The previous entry repaired the *source* of 46 links but not the site: `rehype-markdown-links.js` rewrote `./architecture.md` to the page-relative `./architecture/`, and because Astro builds with `format: 'directory'` a page lives at `/troubleshooting/`, so the browser resolved that to `/troubleshooting/architecture/` and 404'd exactly as before. The plugin now emits root-absolute routes (`{base}/architecture/`), the same form the sidebar already used, which is correct at any nesting depth. It also accepts bare links (`[gate model](gate-model.md)`) rather than passing them through untouched, since those are valid on GitHub, where `docs/` is equally read. Two checks now cover this: `test:rehype` pins the plugin's contract, and `validate:docs-links` resolves every href in the **built** site against the file tree. The built pass is the load-bearing one: the earlier fix made every link look right in the Markdown while the site stayed broken, so a source-only check would have passed it. Both are wired into `npm run quality`, and a `docs-links` CI job builds the site the way the deploy workflow does and runs the guard against that output. One caveat worth knowing locally: `npm run quality` does not build the site, so the built pass skips unless you run `npm run docs:build` first, and the tool says so rather than reporting a bare pass. CI always builds. Closes #52.
- **Docs: in-body links no longer 404 on the published site.** `website/src/rehype-markdown-links.js` only rewrites hrefs that start with `./`, `../`, or `/`, so 32 bare links (`[gate model](gate-model.md)`) shipped to the site verbatim and resolved against the current page directory, returning 404 for anyone who followed one. They now carry a `./` prefix, which the plugin rewrites and which GitHub renders identically. A further 14 links pointed outside `docs/` (`../SECURITY.md`, `../skills/**`); since `docs/` is the site root, those escaped it and 404'd on the site while working on GitHub, so they are now absolute repository URLs that resolve in both places. Nothing in the build fails on an unrewritten link, so the site shipped these silently.
- **Docs: the TEA link pointed at the wrong repository.** README's acknowledgements linked the Test Architect to `bmad-code-org/BMAD-METHOD` rather than to TEA's own repo, `bmad-code-org/bmad-method-test-architecture-enterprise`. TEA is also now listed as a prerequisite in [getting started](docs/getting-started.md): it is a hard dependency (`preflight_check.py` requires `--tea-config`, and the gate reads TEA's `gate-decision.json`) that the install instructions never mentioned, in either profile.
- **Docs: `SECURITY.md` understated what the PreToolUse guard enforces.** The hook-security section called itself "the full account" while describing two of the guard's six invariants, omitting the marker-freshness check, the empty-staged-index denial, the un-skip proof, and the Cross-Session Recall latch. Both it and [architecture](docs/architecture.md) now enumerate all six. Also corrected: the architecture file tree (missing `gate_trail.py`, `status_render.py`, and the `ucg-resolve`/`ucg-status` subskills), the `test/README.md` validator list, and the remaining prose that still described `story_token_budget` as a live guardrail.
- **Gate: `--story` now fails closed on a genuine no-match** (potentially breaking). `scripts/gate_eval.py --story <id>` used to fall back to an unscoped read whenever nothing matched the requested id, so a story that produced no trace artifacts at all silently resolved a *neighbouring* story's gate: an unevaluated story could report `PASS` / `advance`. When the trace dir names its reports or gate decisions per story (`trace-2-1.md`, `gate-decision-4.json`), a `--story` that matches nothing now returns `gate_status: NOT_EVALUATED`, which routes to `escalate`, with a reason naming the absent story. The documented single-story fallback is preserved: a dir whose candidates are all generically named (`trace.md`, `gate-decision.json`) still resolves unscoped. Breaking only for anyone who relied on the silent fallback in a per-story-named dir, where the old behaviour returned another story's verdict.
- **Finalize: the gate trail refuses to render when no story is named** (potentially breaking). `scripts/gate_trail.py` treated `--story` as one of its optional sources, so an invocation naming no story exited `0` and wrote a well-formed `gate-trail.md` carrying `Stories: 0` and no sections, which the stage then names in the run report as delivered evidence: an evidence trail that traces nothing is the failure mode an evidence trail exists to prevent. A blank id (`--story ""`) rendered an anonymous section of nothing but `n/a`. At least one non-empty `--story` is now required, and both shapes exit `2` with a usage line having written nothing, the same invocation-error lane `--run-dir` and `--profile` already occupied. Fail-soft is unchanged for the *sources*: a missing or unreadable checklist, trace report, gate file or baseline still renders `n/a` and the trail still completes. Breaking only for anyone invoking the script with no story ids, where the old behaviour produced an empty document.
- **Formalize: an empty in-scope story set no longer reads `ready`.** `scripts/formalize_check.py` iterates the Epic's story files for every per-story and per-AC check, so an Epic whose story files do not exist scored zero gaps and returned `verdict: ready` with `stories_with_ac: 0`, satisfying the launch gate vacuously. An empty story set now emits a `no_in_scope_stories` mechanical gap (severity high, remediable, naming the Epic and the impl-artifacts dir searched) that counts toward `mechanical_budget` like any other, so the verdict is `remediable`.
- **Formalize: a story that declares no acceptance criteria no longer reads `ready`** (potentially breaking). The empty-story-set guard above keys on the story file being *absent*, but a story file that exists and declares no AC iterates the per-story and per-AC checks zero times just the same, so it contributed no gap and the Epic still scored a clean `verdict: ready` with `stories_with_ac: 0`, which is the verdict the launch gate treats as go. Reproduced on three shapes: an empty file, an `## Acceptance Criteria` heading with no items, and story prose with no AC section at all. Each AC-less story now emits a `story_without_ac` mechanical gap (severity high, remediable, naming the story file) that counts toward `mechanical_budget`, so the verdict is `remediable`. This also closes the landing zone of the other guard's own remediation: the create-story scaffold that clears `no_in_scope_stories` writes story files, and an AC-less stub would otherwise have flipped `remediable` straight back to `ready`. Breaking for any Epic whose stories are stubs, which now blocks at preflight instead of launching.
- **Formalize: a partially seeded Epic no longer reads `ready`** (potentially breaking). The two guards above ask whether the story set is *empty* and whether a resolved story declares no AC. Neither asks whether the resolved files **cover the in-scope keys**, so an Epic seeded with most of its stories iterated the per-story checks over only the stories that exist and scored a clean zero-gap `verdict: ready`. Observed live at 7 of 8 story files, where the kernel returned `mechanical_budget: 0` while an in-scope story had no file and therefore no acceptance criteria for the launch gate to read. In-scope keys that resolve no story file now emit a `story_keys_uncovered` mechanical gap (severity high, remediable, naming the unresolved ids) that counts toward `mechanical_budget`, so the verdict is `remediable`. It fires only when some story files resolved, leaving the zero-story case to `no_in_scope_stories` so a bare Epic is reported once rather than twice, and only when the rollup named keys, since with no keys there is no denominator to compare against. Coverage matches the story **number** (`5-8`) with a required boundary after it, not the whole slug: the number prefix is the only naming rule this module documents, and `bmad-create-story` writes `{story_key}.md` from whatever the operator supplied, so a slug-based rule would report an already-resolved and AC-graded `5-8.md` as missing and refuse to launch a genuinely seeded Epic. The boundary is equally load-bearing in the other direction, since a bare prefix test lets `1-10-foo.md` cover key `1-1` and carry the original fail-open straight through for bare-numeric keys. Breaking for any Epic carrying not-done story keys with no corresponding file, including one deliberately holding stories as unseeded cut-candidates, which now blocks at preflight until those stories are seeded or removed from the sprint status.
- **Health check: a fixed finding no longer suppresses its own regression.** `scripts/health_check_fp.py` closed its disposition vocabulary at `created` / `reacted` / `commented` / `queued`, so there was no way to record that a finding had been *fixed*. A fingerprint therefore suppressed a repeat report forever, and a genuine regression of a fixed defect was silently swallowed, which is the one report the loop most needs to surface. There is now a fifth action, `resolved`, and `seen` returns the suppression verdict rather than mere cache presence: `{"seen": bool, "status": "unseen" | "handled" | "regression" | "unrecognized", "record": ...}`. A `resolved` record does not suppress and still returns the prior record, so the recurrence is reported and linked to the original instead of filed as a first sighting. An unrecognized action does not suppress either, on the same reasoning: a duplicate report is closed automatically by the dedup Action, whereas a silenced regression is caught by nothing. The local queue path no longer overwrites a `resolved` record with `queued`, which would otherwise have re-armed the suppression on the next unattended run. The seen-cache is machine-local, so where a record carries an issue URL the health check now prefers that issue's own open or closed state, which is shared.
- **Health check: an auto-closed duplicate no longer reads as a fix.** The issue-state refinement added above read `gh issue view --json state` and treated any `CLOSED` as a regression trigger. The dedup Action closes duplicates with `state_reason: not_planned`, and a wontfix closes the same way, so a reporter whose submission lost a race held a record pointing at a `CLOSED` issue for a defect nobody had fixed: every subsequent session filed a fresh `REGRESSION` issue against a live defect, which the Action closed as a duplicate again, stably, forever. The check now reads `state,stateReason` and accepts only `CLOSED/COMPLETED` as a fix, while `CLOSED/NOT_PLANNED` keeps the local verdict. It also accepts `MERGED`, because the contributor guide invites the resolving pull request as the recorded URL and `gh issue view` reports `MERGED` rather than `CLOSED` for one, so those records previously never triggered the refinement at all.
