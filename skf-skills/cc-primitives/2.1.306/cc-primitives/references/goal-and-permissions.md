## /goal

- Sets a completion condition; after every turn a small fast model checks it and starts another turn until it holds — the evaluator is a fresh model, not the worker. [EXT:https://code.claude.com/docs/en/goal]
- Session-scoped; one goal per session; a new `/goal <condition>` replaces the active one; `/goal` alone shows status; `/goal clear` (aliases `stop`, `off`, `reset`, `none`, `cancel`) removes it; `/clear` also removes it. [EXT:https://code.claude.com/docs/en/goal]
- Setting a goal starts a turn immediately with the condition as directive. [EXT:https://code.claude.com/docs/en/goal]
- The evaluator does not run commands or read files, so the condition must be demonstrable from Claude's own output. [EXT:https://code.claude.com/docs/en/goal]
- Conditions are capped at 4,000 characters; bound runtime with a clause such as "or stop after 20 turns". [EXT:https://code.claude.com/docs/en/goal]
- Resume (`--continue`, `--resume`) restores an active goal; the turn count, timer and token baseline reset. [EXT:https://code.claude.com/docs/en/goal]
- `claude -p "/goal …"` runs the loop to completion in one invocation; add `--output-format stream-json --verbose` to see progress. [EXT:https://code.claude.com/docs/en/goal]
- Implemented as a session-scoped prompt-based Stop hook using the configured small fast model (`ANTHROPIC_DEFAULT_HAIKU_MODEL` changes it). [EXT:https://code.claude.com/docs/en/goal] [EXT:https://code.claude.com/docs/en/hooks]
- Verdicts: *Not yet met* (keep working, reason as guidance), *Met* (goal cleared, achieved entry), *Impossible* (cleared, failed entry). [EXT:https://code.claude.com/docs/en/goal]
- The loop stops with the goal still set if Claude answers the evaluator without tool use several turns in a row. An error you have to fix clears the goal: an authentication failure when Claude Code manages its own credentials, an exhausted credit balance, a context overflow auto-compaction couldn't clear, or an unavailable model. After any other error the goal stays set. In an interactive session on v2.1.269 or later, a failure that tends to clear on its own (overloaded server, dropped connection) is retried automatically and the goal pauses after three retries; a failure a retry would only repeat (API rate limit, usage limit, a hook that ended the turn) pauses the goal. `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0` turns retries and check-ins off. [EXT:https://code.claude.com/docs/en/goal]
- Evaluation is skipped while a subagent or background shell is still running; check-ins after 30 minutes of waiting, at most three idle check-ins between prompts. [EXT:https://code.claude.com/docs/en/goal]
- Unavailable when `disableAllHooks` is true or `allowManagedHooksOnly` is set in managed settings. [EXT:https://code.claude.com/docs/en/goal]
- Auto mode removes per-tool prompts, `/goal` removes per-turn prompts; a goal does not change the permission mode. [EXT:https://code.claude.com/docs/en/goal]

## Permission modes

| Mode | Behaviour |
|------|-----------|
| `default` / `manual` | Built-in start for `-p` and Agent SDK sessions; `manual` is an alias (v2.1.200+) [EXT:https://code.claude.com/docs/en/permission-modes] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `acceptEdits` | Reads, file edits and common filesystem commands without asking [EXT:https://code.claude.com/docs/en/permission-modes] [EXT:https://code.claude.com/docs/en/headless] |
| `plan` | Researches and proposes without changing; keeps its blocks in `-p` runs [EXT:https://code.claude.com/docs/en/permission-modes] |
| `auto` | Everything without asking, with background classifier checks; built-in start for interactive terminal/VS Code from v2.1.283 [EXT:https://code.claude.com/docs/en/permission-modes] |
| `dontAsk` | File reads in the working directories and pre-approved tools; denies anything that would prompt, though an installed mod can still approve some of those calls; not in the Shift+Tab cycle [EXT:https://code.claude.com/docs/en/permission-modes] |
| `bypassPermissions` | Skips permission prompts and safety checks, except for the actions no mode auto-approves (explicit ask rules, `AskUserQuestion` and `requiresUserInteraction` MCP tools, `rm`/`rmdir` of a critical path, and others), which still prompt, or are denied in a `-p` run; isolated containers/VMs only; must be enabled at launch [EXT:https://code.claude.com/docs/en/permission-modes] |

- Starting mode comes from `--permission-mode` / `--dangerously-skip-permissions`, then `permissions.defaultMode`; `defaultMode` `auto` and `bypassPermissions` have no effect in project or local settings files (a project/local `auto` falls back to the built-in default, a project/local `bypassPermissions` starts the session in Manual). [EXT:https://code.claude.com/docs/en/permission-modes] [EXT:https://code.claude.com/docs/en/settings]
- Shift+Tab: from auto the first press switches to default, then the cycle runs default → acceptEdits → plan, then the enabled optional modes (bypass first, auto last); `--allow-dangerously-skip-permissions` adds bypass to the cycle without activating it. [EXT:https://code.claude.com/docs/en/permission-modes]
- `claude -p` and Agent SDK runs with no mode set start in Manual (v2.1.302+): a call needing approval is denied unless an allow rule, hook, `canUseTool` callback or `--permission-prompt-tool` approves it. [EXT:https://code.claude.com/docs/en/permission-modes]
- Deny rules block in every mode, including bypass; allow rules have no effect in bypass. [EXT:https://code.claude.com/docs/en/permission-modes]
- `--dangerously-skip-permissions` equals `--permission-mode bypassPermissions`; `permissions.disableBypassPermissionsMode: "disable"` blocks it; `permissions.disableAutoMode: "disable"` removes auto. [EXT:https://code.claude.com/docs/en/permission-modes]
- Auto mode pauses after 3 consecutive or 20 total classifier blocks; in `-p` without a prompt tool the blocked action is skipped and the run continues. [EXT:https://code.claude.com/docs/en/permission-modes]
- Auto mode blocks launching unsandboxed autonomous loops (e.g. `--dangerously-skip-permissions`) and sending keystrokes to its own tmux pane; entering auto drops broad allow rules such as `Bash(*)`. [EXT:https://code.claude.com/docs/en/permission-modes]
- In auto mode a subagent's frontmatter `permissionMode` is ignored. [EXT:https://code.claude.com/docs/en/permission-modes]
- If auto is selected but unavailable, the session starts in Manual. [EXT:https://code.claude.com/docs/en/permission-modes]

## Permission rules

- Rules take the form `Tool` or `Tool(specifier)` in `permissions.allow`, `ask` and `deny`; Claude Code enforces them, not the model. [EXT:https://code.claude.com/docs/en/permissions]
- Rules are evaluated deny, then ask, then allow, and the first match decides; specificity doesn't change the order, so an allow rule can't carve an exception out of a deny rule, and a matching ask rule prompts even when a narrower allow rule matches. [EXT:https://code.claude.com/docs/en/permissions]
- A bare tool name in a deny rule (`Bash`, or the equivalent `Bash(*)`) removes the tool from Claude's context; a scoped rule such as `Bash(rm *)` blocks only matching calls. [EXT:https://code.claude.com/docs/en/permissions]
- Deny and ask rules can match a top-level input parameter on any built-in tool with `Tool(param:value)`, such as `Agent(model:opus)`. For an MCP tool, pass the deny rule with `--disallowedTools`, because a settings file's `mcp__` rule with parentheses is skipped. They can't match a tool's primary content field: `Bash(command:rm *)` is ignored with a startup warning. They also take tool-name globs (`"*"`, `"mcp__*"`); allow rules take them only after a literal `mcp__<server>__` prefix. [EXT:https://code.claude.com/docs/en/permissions]
- **Wildcards:** in a Bash rule `*` matches any text, spaces included, and a rule with no `*` matches one exact command. Everything before the first `*` is matched as written, so put the `*` after the subcommand: `Bash(git log *)` allows only `git log` commands, `Bash(git *)` every git command. [EXT:https://code.claude.com/docs/en/permissions]
- **Trailing ` *` and `:*`:** a `*` at the end with a space before it also matches the bare command (`Bash(ls *)` matches `ls`), but only when it is the rule's only wildcard (`Bash(* --help *)` doesn't match `npm --help`). The space is part of the rule: `Bash(ls *)` doesn't match `lsof`, `Bash(ls*)` does. `Bash(ls:*)` matches the same commands as `Bash(ls *)`; `:*` is recognized only at the end of a pattern, so the colon in `Bash(git:* push)` is literal. [EXT:https://code.claude.com/docs/en/permissions]
- **Compound commands:** `&&`, `||`, `;`, `|`, `|&`, `&` and newlines separate subcommands, and an allow rule must match each one, so `Bash(safe-cmd *)` doesn't allow `safe-cmd && other-cmd`. Deny and ask rules apply when any subcommand matches, including one nested in a subshell, a command substitution or a `for` body. A command that ends in `&&` or `||` with nothing after it is unparseable and isn't split for allow matching. "Yes, and don't ask again" on a compound command saves a separate rule for each subcommand that needs approval, at most 5. [EXT:https://code.claude.com/docs/en/permissions]
- **Wrappers stripped before matching:** `timeout`, `time`, `nice`, `nohup`, `stdbuf`, the shell builtins `command` and `builtin`, zsh's `noglob`, and bare `xargs` (no flags), so `Bash(npm test *)` matches `timeout 30 npm test`. Not stripped: `command -v`, zsh's `nocorrect`, and `xargs` with flags. The list is built in and not configurable. Environment runners (`direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec`) aren't on it, so `Bash(devbox run *)` matches whatever comes after `run`; write one rule per runner and inner command, such as `Bash(devbox run npm test)`. [EXT:https://code.claude.com/docs/en/permissions]
- **Leading environment assignments:** Claude Code also strips a leading assignment of certain known-safe environment variables, so `Bash(npm test *)` matches `NODE_ENV=test npm test`; the page gives `NODE_ENV` as its example and lists no other variable. The page's sentences on the assignment rule: "An allow rule won't match past an assignment of any other variable. A deny or ask rule matches past any leading assignment, so `Bash(rm *)` in deny still matches `FOO=bar rm -rf tmp/`." [EXT:https://code.claude.com/docs/en/permissions]
- **What a prefix rule can't approve:** exec wrappers such as `watch`, `setsid`, `ionice` and `flock`, and `find` with an action such as `-exec`, `-delete` or `-fprint`, or with `-files0-from`, prompt in Manual mode; an exact-match rule for the full command string, with no `*`, approves one invocation. [EXT:https://code.claude.com/docs/en/permissions]
- **Not a security boundary:** a Bash rule matches the command text, not the program, so `Bash(rm *)` in deny doesn't stop `/bin/rm -rf build/` or `bash -c 'rm -rf build/'`; enforce with sandboxing or a PreToolUse hook. A built-in set of read-only commands (`ls`, `cat`, `grep`, `find`, read-only `git` and more) runs without a prompt in every mode, except where `permissions.blockReadsOutsideWorkingDirectories` fences paths outside the working directories and in the Manual-mode cases the page lists (an unquoted glob on a command with write-capable flags, writes to `PATH`/`IFS`, a command the analysis can't parse or one over 10,000 characters, and others); in auto mode they can wait for the classifier. The set isn't configurable: add an ask or deny rule to gate one. [EXT:https://code.claude.com/docs/en/permissions]
- **Rules and hooks:** PreToolUse decisions don't bypass deny and ask rules, and a hook that exits 2 blocks before rules are evaluated, even when an allow rule matches, so allowing `Bash` plus a PreToolUse hook that rejects a few commands runs everything else without prompts. Without managed settings or a Team or Enterprise `/login`, an installed mod can approve a call that a deny rule refuses or a PreToolUse hook blocked. [EXT:https://code.claude.com/docs/en/permissions]
- **Across settings levels:** a deny at any level can't be allowed by another, so a managed deny can't be overridden by `--allowedTools`, and a user-level deny blocks a project-level allow. [EXT:https://code.claude.com/docs/en/permissions]

## Auto Mode configuration

- Deny and explicit ask rules are evaluated before the classifier; content-scoped `permissions.ask` forces a prompt even in auto; `permissions.deny` cannot be overridden. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- By default the classifier trusts only the working directory and the current repo's remotes as configured when the session started (a remote added or repointed mid-session isn't trusted). It allows pushes to any branch of that repo, including the default branch, and PR creation; a non-default branch named as a deploy or publication target (`production`, `release`, `gh-pages`) isn't covered by that default, and a push's content is still checked. [EXT:https://code.claude.com/docs/en/auto-mode-config] [EXT:https://code.claude.com/docs/en/permission-modes]
- `autoMode` is ignored in `.claude/settings.json` and `.claude/settings.local.json`; put it in `~/.claude/settings.json`, managed settings or `--settings`. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- Fields: `environment` (usually all you need), `allow`, `soft_deny` (user intent can clear), `hard_deny` (unconditional); include `"$defaults"` to keep built-ins — an array without it replaces the built-in list. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- `autoMode.classifyAllShell: true` routes every shell command through the classifier. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- CLI: `claude auto-mode defaults`, `config`, `critique`, `reset`; `/auto-mode-setup` drafts `environment` entries. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- Denials land in `/permissions` → Recently denied; a `PermissionDenied` hook receives the denied `tool_input`; a `PreToolUse` hook can checkpoint commands by full text. [EXT:https://code.claude.com/docs/en/auto-mode-config]
- Classifier requests go to Claude Sonnet 5 by default; `CLAUDE_CODE_AUTO_MODE_MODEL` (v2.1.302+) runs the classifier on another full model ID. [EXT:https://code.claude.com/docs/en/permission-modes]
- `useAutoModeDuringPlan` (default on) lets the classifier review shell commands while planning. [EXT:https://code.claude.com/docs/en/permission-modes]
