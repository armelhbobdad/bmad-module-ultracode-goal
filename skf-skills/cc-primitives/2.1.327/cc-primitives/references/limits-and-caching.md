## Rate limits and usage limits under -p

- Claude Code retries transient failures up to 10 times with exponential backoff before showing an error, so an error that surfaces has already had the retries that apply to it. [EXT:https://code.claude.com/docs/en/errors]
- The retry set includes temporary `429` throttles but not a gateway's spend-limit `429`; on a claude.ai subscription it includes `429` throttles that carry no plan quota headers (before v2.1.199 those were retried only for API key and Enterprise sign-ins). [EXT:https://code.claude.com/docs/en/errors]
- A server error or overloaded response that arrives after Claude finished thinking but before any text or tool call is retried, a server error at that point up to two times (before v2.1.284 the turn ended). A server error, dropped connection or stalled stream that arrives after Claude completed a text block or tool call, or started one after finishing its thinking, but before the response finishes is not re-run, since that could execute the same tool calls twice: Claude Code keeps what Claude completed, runs any tool calls it finished, and continues the turn from their results. [EXT:https://code.claude.com/docs/en/errors]
- In a `-p` run, a cut-off main-conversation response that contains text but no tool calls is continued automatically (v2.1.246+), up to three times in a row, before the `The response above may be incomplete` notice shows. With `--output-format json` or `stream-json` that notice is reported in the `result` field; to continue the turn once the connection is stable, resume the session and send `continue`. [EXT:https://code.claude.com/docs/en/errors]

| Condition | Text shown | Retry and recovery |
|-----------|------------|--------------------|
| Server-side throttle (no unified quota headers) | `API Error: Server is temporarily limiting requests (not your usage limit)` | Retried with backoff before being shown, for every auth method from v2.1.199 [EXT:https://code.claude.com/docs/en/errors] |
| Rate limit of an API key, Amazon Bedrock or Google Cloud project | `API Error: Request rejected (429) · this may be a temporary capacity issue.` | Temporary throttles are retried; the docs advise reducing concurrency (fewer parallel subagents) or a smaller model for high-volume scripted runs [EXT:https://code.claude.com/docs/en/errors] |
| `529` overload | `API Error: Repeated 529 Overloaded errors.` | Not a usage limit and not counted against quota; capacity is tracked per model, so switching models keeps you working. Retrying can stop before the retry budget (with an API key on an Opus model, at the third `529`), and with a fallback model set Claude Code switches to it instead of showing the error [EXT:https://code.claude.com/docs/en/errors] [EXT:https://code.claude.com/docs/en/env-vars] |
| Session or weekly limit (subscription) | `You've hit your session limit · resets 3:45pm`, `You've hit your weekly limit · resets Mon 12:00am` | Requests are blocked until the reset time in the message; both limits span all models, so switching models doesn't restore access [EXT:https://code.claude.com/docs/en/errors] |
| Opus or Sonnet limit | `You've hit your Opus limit · resets 3:45pm` (or `Sonnet`) | Applies only to that model family; a model outside the family keeps working [EXT:https://code.claude.com/docs/en/errors] |
| Usage-credits spend limit | `You've hit your monthly spend limit` and variants | When a plan window is what ran out, the message names its reset (`· your session limit resets 3:45pm`) and access returns then [EXT:https://code.claude.com/docs/en/errors] |
| Claude apps gateway spend cap | `spend limit reached · resets Dec 1` | Each blocked `429` is marked `x-should-retry: false`, so it is shown without retrying; blocked until the operator raises the cap or, for a cap above $0, it resets [EXT:https://code.claude.com/docs/en/errors] |

- `fallbackModel` (array of model aliases or IDs, scope Any file; `--fallback-model` takes precedence for one session) names backup models that Claude Code tries in order when the primary is overloaded or unavailable; it keeps at most three distinct allowed models from the list, and the key doesn't merge across settings files (the highest-precedence file supplies the whole chain). A switch lasts the rest of the turn, and the next message tries the primary first; unset (the default), Claude Code retries the same model and then surfaces the server's error. [EXT:https://code.claude.com/docs/en/settings-reference]
- In `-p`, an exported `ANTHROPIC_API_KEY` is always used when present, instead of a claude.ai login; a stray key can route requests through a low-tier key instead of the subscription. [EXT:https://code.claude.com/docs/en/errors]
- Usage counts against the session and weekly allowances at the same time, so a large workflow fan-out can exhaust the weekly allowance before the session window resets. [EXT:https://code.claude.com/docs/en/errors] On Team and Enterprise, each seat draws on an allowance with a rolling five-hour window and a weekly window, shared with Claude chat and Cowork. [EXT:https://code.claude.com/docs/en/costs]
- Background sessions consume subscription usage like interactive ones, so ten in parallel use quota roughly ten times as fast as one [EXT:https://code.claude.com/docs/en/agent-view]; a subagent's requests count toward the same usage limits as the main conversation. [EXT:https://code.claude.com/docs/en/sub-agents]
- Before a window runs out Claude Code can warn, as in `You've used 85% of your session limit · resets 3:45pm`; a custom status line's `rate_limits` fields show the remaining allowance. [EXT:https://code.claude.com/docs/en/errors] `rate limited until <time>` in `/usage` means plan limits can't be fetched again until then, not that work is limited. [EXT:https://code.claude.com/docs/en/costs]
- `claude -p` exits 0 on success and non-zero when the run fails; an invalid flag is reported on stderr before the run starts, and a failure inside the run, such as missing authentication, is printed as the result on stdout. [EXT:https://code.claude.com/docs/en/headless]
- With `stream-json`, a `system/api_retry` event precedes each retry of a retryable error, with `attempt`, `max_retries` (total retries permitted for that failure's cause), `retry_delay_ms`, `error_status` (`null` when no HTTP response came), an optional `no_response` object when the attempt got no response headers in time (`waited_ms`, `retry_wait_ms`; v2.1.261+) and `error`: one of `authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `max_output_tokens`, `cloud_credential_error`, `unknown`. From v2.1.246 the first two retries after an `apiKeyHelper` `401` or `403` emit no event but still count toward `attempt`. [EXT:https://code.claude.com/docs/en/headless] Formats: [Output formats](headless-and-cli.md#output-formats).
- A `StopFailure` hook runs instead of `Stop` when a turn ends on an API error. Its `error` values include `rate_limit`, `billing_error` and `server_error` (an HTTP `529` is reported as `server_error`), the optional `last_assistant_message` holds the API error string, and it has no decision control: output and exit code are ignored except `terminalSequence`. [EXT:https://code.claude.com/docs/en/hooks] Events: [Hooks](hooks.md#events).
- A subagent whose run ends on an API error, such as a usage limit or a repeated server error, reports the failure to Claude. In the foreground, a subagent cut off by a rate limit, overload or server error after producing text returns that partial output with a note that it didn't finish; one that produced nothing, or only tool calls, fails with `Agent terminated early due to an API error: <error detail>` (that message needs v2.1.199+). [EXT:https://code.claude.com/docs/en/sub-agents] [EXT:https://code.claude.com/docs/en/errors] In the background, the subagent is marked failed, and the message Claude receives names the API error and includes its last output. [EXT:https://code.claude.com/docs/en/sub-agents]
- When a mid-stream cut-off leaves a subagent's partial response with text but no tool calls, Claude Code first prompts the subagent to continue, in interactive sessions too, and the run ends on the error only once those continuations are used up. [EXT:https://code.claude.com/docs/en/sub-agents]

## Waiting at a usage limit

- In an interactive session signed in with a claude.ai subscription, Claude Code waits in the open session when a usage limit stops Claude mid-task and continues the task after the reset; this is on by default and needs v2.1.234+. [EXT:https://code.claude.com/docs/en/interactive-mode]
- At the reset it shows `Usage limit reset · Continuing automatically` and prompts Claude to pick the task up where it stopped, without resending the last message. Permission prompts still apply, and a repeat hit starts the wait again. [EXT:https://code.claude.com/docs/en/interactive-mode]
- After three automatic continuations it stops with `Automatic continue stopped after repeated usage-limit hits`, and `/rate-limit-options` chooses what to do next; a new prompt, or a wait picked from that menu, resets the count. [EXT:https://code.claude.com/docs/en/interactive-mode]
- Claude Code doesn't start the wait on its own in Remote Control or agent team teammate sessions (a person at that terminal can still start one), when the reset is more than 24 hours away (a weekly limit can reset days out), or at an Opus or Sonnet limit while running a model outside that family (`opusplan` and other model settings that run plan mode on the limited family don't get this exception). In those cases, and whenever automatic continue is off, the usage-limit options menu opens once per reset window when a limit is hit at your own terminal. [EXT:https://code.claude.com/docs/en/interactive-mode]
- The wait is not offered at all in background sessions or `-p` runs (the menu row isn't available), with API keys, cloud providers or usage-based billing (metered per request, no reset), or behind an LLM gateway without a saved claude.ai login. [EXT:https://code.claude.com/docs/en/interactive-mode]
- A wait ends without continuing when you send a prompt, exit (resuming doesn't restart it), the conversation changes hands (including a move to a background session), the setting turns off or the reset moves past 24 hours (waits Claude Code started only), or a `UserPromptSubmit` hook or a failure before the model stops the continuation. [EXT:https://code.claude.com/docs/en/interactive-mode]
- `autoContinueAtUsageLimit` (Boolean, default `true`, v2.1.234+) is read only from user settings, `--settings` and managed settings; when none of those sets it, a project or local file that sets it turns the feature off rather than being ignored. With `false`, Claude Code doesn't start the wait itself, though a user can still start one from the menu. [EXT:https://code.claude.com/docs/en/settings-reference]
- The `/config` row **Continue automatically at usage limit** writes user settings and is hidden while managed settings or `--settings` set the key. [EXT:https://code.claude.com/docs/en/settings-reference] `/config autoContinueAtUsageLimit=false` works, including with `-p`, but the `key=value` form can't turn it back on. [EXT:https://code.claude.com/docs/en/interactive-mode] To control for a fleet whether Claude Code starts the wait on its own, set the key in managed settings. [EXT:https://code.claude.com/docs/en/costs]
- `/rate-limit-options` requires a claude.ai subscription, and its wait-and-continue rows need v2.1.234+. [EXT:https://code.claude.com/docs/en/commands] The Desktop Code tab's **Auto-continue when limits reset** checkbox sits on the session-limit card only (not the weekly-limit card) and is separate from the CLI setting. [EXT:https://code.claude.com/docs/en/errors]
- Notification hooks receive `quota_auto_resume_fired` (the task continued after a usage limit), `quota_auto_resume_stale` (the limit reset while the computer slept for more than about 30 minutes, so Claude Code waits for `Enter`) and `quota_auto_resume_disabled`, all three v2.1.234+. `quota_auto_resume_disabled` fires when Claude Code ends its wait without continuing: the setting turned off or the reset moved more than 24 hours away during a wait it started on its own, the continued task kept hitting the limit, or the continuation was blocked before it reached the model; it doesn't fire on `Esc`, `Ctrl+C` or **Don't continue automatically**. [EXT:https://code.claude.com/docs/en/hooks]
- Background sessions, Remote Control, agent team teammates and Agent SDK-hosted sessions end the turn when the Fable usage-credits consent prompt closes unanswered, with a message containing `the prompt to confirm went unanswered`. [EXT:https://code.claude.com/docs/en/errors]
- `CLAUDE_CODE_RETRY_WATCHDOG` makes a session that hits a usage limit wait out the remaining window ([Retry watchdog](#retry-watchdog)). [EXT:https://code.claude.com/docs/en/env-vars]

## Retry watchdog

- `CLAUDE_CODE_RETRY_WATCHDOG=1` (v2.1.186+) is for unattended sessions such as eval harnesses, CI jobs or remote workers: it retries `429` and `529` capacity errors indefinitely instead of failing after `CLAUDE_CODE_MAX_RETRIES` attempts. [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors]
- It backs off up to 5 minutes between attempts, or until the limit resets when the response carries a rate-limit reset time, so a session that hits a usage limit waits out the remaining window. [EXT:https://code.claude.com/docs/en/env-vars]
- From v2.1.239 a standard-speed request fails at once on a `429` that reports a spend limit or exhausted usage credits, even a gateway spend cap that resets on a schedule; earlier versions retried these indefinitely. Fast-mode requests are covered on the fast-mode page. [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors]
- On v2.1.199+ it also raises the default retry count for other transient errors (server errors, timeouts, dropped connections) to 300, roughly three hours of backoff, and removes the cap of 15 on an explicitly set `CLAUDE_CODE_MAX_RETRIES`. [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors]
- When a streaming request misses its first-byte deadline, it keeps re-sending within the budget instead of ending the turn with `No response from API`, and the `529` backoff variables have no effect while it is `1`. [EXT:https://code.claude.com/docs/en/errors]
- For unattended sessions that must wait through longer outages, the docs point to the watchdog rather than to raising `CLAUDE_CODE_MAX_RETRIES`. [EXT:https://code.claude.com/docs/en/env-vars]

| Variable | Default | Effect |
|----------|---------|--------|
| `CLAUDE_CODE_RETRY_WATCHDOG_MAX_WAIT_MS` | unset (no limit) | Per-request cap on time spent waiting out `429` and `529` errors under the watchdog; once spent, the next such error ends the request. A positive whole number in plain digits, such as `1800000` for 30 minutes; v2.1.295+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |
| `CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS` | no cap | With the watchdog set, the longest one request waits for a plan usage limit, such as the session or weekly limit, to reset; a reset further away fails the request at once, unless usage credits have room or the API couldn't check them, in which case it is retried and fails if the cap passes first; v2.1.301+ [EXT:https://code.claude.com/docs/en/errors] |
| `CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS` | unset (no checks) | Minimum interval between checks of whether a usage limit was already lifted while a request waits under the watchdog; a lifted limit sends the request at once. Plain digits from `60000` to `10800000` (out of range means no checks); checks run only for a claude.ai subscription's session or weekly limit while usage credits aren't in use, and not while `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set; v2.1.305+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |

- Set these in the shell before launching, or under the `env` key of a settings file, which Claude Code reads directly so it applies however `claude` is launched. [EXT:https://code.claude.com/docs/en/env-vars] Project and local `env` values apply at startup in `-p` mode, which never shows the trust dialog. [EXT:https://code.claude.com/docs/en/settings-reference] Files: [Settings files](memory-and-settings.md#settings-files).

## Other retry and timeout variables

| Variable | Default | Effect |
|----------|---------|--------|
| `CLAUDE_CODE_MAX_RETRIES` | `10` | Retry attempts for failed API requests; capped at 15 as of v2.1.186, and from v2.1.199 the watchdog raises the default and removes the cap; lower it to surface failures faster in scripts [EXT:https://code.claude.com/docs/en/errors] [EXT:https://code.claude.com/docs/en/env-vars] |
| `CLAUDE_CODE_OVERLOADED_RETRY_BASE_DELAY_MS` | `500` | Starting backoff between retries of a `529`; whole milliseconds from 500 to 32000 in plain digits (other values count as unset); no effect with the watchdog set to `1` or for a request sent in fast mode; v2.1.292+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |
| `CLAUDE_CODE_OVERLOADED_RETRY_MAX_DELAY_MS` | `32000` | Backoff ceiling for `529` retries; 32000 to 300000 in plain digits (other values count as unset), values above 64000 need v2.1.323+; same no-effect cases; v2.1.296+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |
| `API_TIMEOUT_MS` | `600000` (10 minutes) | Time each attempt has to receive response headers, not a limit on how long a stream runs after that; maximum `2147483647`; a positive value also bounds each non-streaming attempt; `0` removes the limit (v2.1.305+), but a non-streaming attempt still times out after 300 seconds in a local session [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |
| `CLAUDE_CODE_NONSTREAMING_TIMEOUT_RETRIES` | unset | Limit on re-sends of a non-streaming request that times out; `0` fails on the first timeout; v2.1.285+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |
| `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS` | unset | First-byte deadline of a streaming request where that deadline runs; a value of 1 or more is clamped to between 10 seconds and 30 minutes for the first attempt, plus one second per 32KB of request body; v2.1.242+ [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/errors] |

- A non-streaming attempt ends at its request timeout (`API_TIMEOUT_MS` when positive, otherwise 300 seconds in a local session) or at the body idle timeout (5 to 6 minutes without a response, however high `API_TIMEOUT_MS` is, where it runs and isn't turned off), whichever comes first. [EXT:https://code.claude.com/docs/en/errors]
- The re-send after a missed first-byte deadline waits one second less than `API_TIMEOUT_MS` (just under 10 minutes by default; on Amazon Bedrock, the first attempt's deadline; a different rule applies when it is `0`). When that passes too, the turn ends with `API Error: No response from API (...)` unless the watchdog is set. [EXT:https://code.claude.com/docs/en/errors]
- Neither first-byte wait exceeds one second less than a positive `API_TIMEOUT_MS`, and a positive `API_TIMEOUT_MS` under 11 seconds turns the deadline off. In a Claude apps gateway session the deadline runs only when `CLAUDE_STREAM_FIRST_BYTE_TIMEOUT_MS` is set to `1` or more (ignored there before v2.1.307). [EXT:https://code.claude.com/docs/en/errors]

## Workflows at limits and concurrency

- `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` sets how many agents one workflow run executes at once, from `1` to `256`. By default a run executes up to 16, fewer when Claude Code has fewer CPUs (including inside a CPU-limited container), and queued `agent()` calls wait for a free slot. [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/workflows]
- It takes plain digits only (out-of-range values and other spellings keep the default), each running agent's transcript stays in memory so higher values raise memory use, and it needs v2.1.269+. [EXT:https://code.claude.com/docs/en/env-vars]
- One `parallel()` or `pipeline()` call takes up to 4,096 items (a longer list is rejected with an error), and a run is capped at 1,000 agents total. [EXT:https://code.claude.com/docs/en/workflows]
- An `agent()` call resolves to `null` if it is stopped mid-run or hits an unrecoverable API error, and `pipeline()` keeps each `null` in its results array. [EXT:https://code.claude.com/docs/en/workflows]
- A run pauses on its own only for agent permission prompts and a usage-limit wait. [EXT:https://code.claude.com/docs/en/workflows]
- When an agent hits the claude.ai usage limit and every condition below holds, the run pauses instead of failing it: affected agents wait, no new agents start, and the run continues on its own shortly after the reset. This needs v2.1.271+, or v2.1.319+ in the Desktop Code tab; earlier versions fail the affected agents. [EXT:https://code.claude.com/docs/en/workflows]
- Pause conditions; when one doesn't hold, the affected agent fails: [EXT:https://code.claude.com/docs/en/workflows]
  - A claude.ai subscription without usage-based billing, in one of two session types: an interactive terminal session (not `claude -p`, the Agent SDK, a background session, or a Remote Control or agent team teammate session), or a local session started in the Code tab (not an SSH, WSL, Dispatch or scheduled task session, one started from Remote Control or through a corporate launcher, or one running while `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set). [EXT:https://code.claude.com/docs/en/workflows]
  - `autoContinueAtUsageLimit` on; turning it off during a wait ends the wait and fails the waiting agents. [EXT:https://code.claude.com/docs/en/workflows]
  - In the Code tab, the **Auto-continue when limits reset** checkbox on a session-limit card checked, as it is by default; unchecking it stops pausing in Code tab sessions unless managed settings set `autoContinueAtUsageLimit` to `true`. [EXT:https://code.claude.com/docs/en/workflows]
  - A reset within 24 hours, and a run that hasn't already waited twice (a third hit fails the agent). [EXT:https://code.claude.com/docs/en/workflows]

| Session type | Workflow agent at a usage limit |
|--------------|---------------------------------|
| Interactive terminal session meeting the conditions | Run pauses and continues after the reset [EXT:https://code.claude.com/docs/en/workflows] |
| `claude -p`, Agent SDK | Affected agent fails [EXT:https://code.claude.com/docs/en/workflows] |
| Background session, Remote Control or agent team teammate session | Affected agent fails [EXT:https://code.claude.com/docs/en/workflows] |

- Time an agent spends waiting on a usage-limit reset doesn't count toward its stall window. [EXT:https://code.claude.com/docs/en/workflows]
- To finish a run whose agents failed at the limit, ask Claude to relaunch the workflow after the reset. On v2.1.318+ an agent that failed at a usage limit runs again while completed agents return saved results, but if the script called another agent after the failure and that agent returned a result, every agent the script starts after the failed one also runs again. [EXT:https://code.claude.com/docs/en/workflows]
- A run doesn't continue on its own after the session is backgrounded or exits; it continues only when Claude relaunches it with a `Workflow` call, and a relaunch that finds no saved results fails with `nothing to resume`. [EXT:https://code.claude.com/docs/en/workflows] More: [Workflow limits and cost](subagents-and-workflows.md#workflow-limits-and-cost).

## /goal at limits

- `claude -p "/goal <condition>"` runs the loop to completion in a single invocation; interrupt the process with Ctrl+C to stop it before it resolves. With the default text output the final response prints only when the loop ends, and `--output-format stream-json --verbose` emits each message as the loop runs. [EXT:https://code.claude.com/docs/en/goal] See [/goal](goal-and-permissions.md#goal).
- When a turn fails, Claude Code clears the goal only for an error you have to fix, such as an exhausted credit balance, an authentication failure while Claude Code manages its own credentials, a context overflow auto-compaction couldn't clear, or a model that isn't available. The warning starts `Goal cleared after an unrecoverable error` and ends `Run /goal again to continue`; after any other error the goal stays set. [EXT:https://code.claude.com/docs/en/goal]
- In an interactive session on v2.1.269+, a failure that tends to clear (an overloaded server, a dropped connection) is retried with a `Goal still active` notice showing the wait, and the goal pauses after three automatic retries. A failure a retry would only repeat (an API rate limit, a claude.ai usage limit, a hook that ended the turn) pauses it with a `Goal paused` notice naming the cause. [EXT:https://code.claude.com/docs/en/goal]
- If the session is waiting to continue automatically at a usage-limit reset, Claude resumes work toward the goal then [EXT:https://code.claude.com/docs/en/goal]; automatic continue stops after three continuations for a `/goal` that runs through several reset windows. [EXT:https://code.claude.com/docs/en/interactive-mode]
- `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0` turns goal automatic retries off along with check-ins; the default is `30`, values are whole minutes in plain digits up to `10080`, and it needs v2.1.234+. [EXT:https://code.claude.com/docs/en/goal] [EXT:https://code.claude.com/docs/en/env-vars]

## Prompt-cache TTLs

- Claude Code picks the TTL per request from two fixed buckets: the main conversation (interactive turns, `-p` runs, Agent SDK turns, and the helpers run inline with them) and everything else, such as subagents, workflows, in-process teammates, forks, compaction and session titles. [EXT:https://code.claude.com/docs/en/prompt-caching]
- Unless you choose a TTL, Claude Code requests the one-hour TTL only on a Claude subscription within the plan's included usage. [EXT:https://code.claude.com/docs/en/prompt-caching]

| Request | Claude subscription, within plan usage | Usage credits, API key or cloud provider |
|---------|----------------------------------------|------------------------------------------|
| Main conversation, including `claude -p` and Agent SDK turns | 1 hour | 5 minutes [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Subagents | 5 minutes | 5 minutes [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Workflow agents | 5 minutes | 5 minutes [EXT:https://code.claude.com/docs/en/workflows] [EXT:https://code.claude.com/docs/en/prompt-caching] |
| In-process teammates, forks, compaction, session titles | 5 minutes | 5 minutes [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Server-controlled helper requests | 1 hour | 5 minutes [EXT:https://code.claude.com/docs/en/prompt-caching] |

- The bucket list names neither background sessions nor teammates other than in-process ones; see [Not stated in the docs](#not-stated-in-the-docs). [EXT:https://code.claude.com/docs/en/prompt-caching]
- Once a subscription goes over its plan limit and draws on usage credits, the main conversation drops to five minutes, which charges a lower cache-write rate, unless you choose a TTL yourself. [EXT:https://code.claude.com/docs/en/prompt-caching]
- With an API key, Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry or Claude Platform on AWS, the main conversation's turns default to five minutes, so many short sessions on the same system prompt and context with gaps over five minutes each pay full input price. [EXT:https://code.claude.com/docs/en/agent-sdk/cost-tracking]
- Each request that hits the cache resets the timer, and the cache counts as warm for one TTL after Claude Code last sent a request or Claude last responded. [EXT:https://code.claude.com/docs/en/prompt-caching]
- The one-hour TTL bills cache writes at a higher rate, so it costs more on short bursts of work that never idle past five minutes. [EXT:https://code.claude.com/docs/en/prompt-caching]
- One hour through intermediaries: an LLM gateway set with `ANTHROPIC_BASE_URL` must forward the `anthropic-beta` header unchanged; on a Claude apps gateway an administrator requests it in a gateway policy; on Amazon Bedrock, caching support, minimum cacheable prefix length and one-hour availability vary by model. [EXT:https://code.claude.com/docs/en/prompt-caching]

## Changing the TTL

| Control | Set in | Applies to | Notes |
|---------|--------|------------|-------|
| `promptCacheTtl` | Settings, any file (user, project, local, managed) | Main conversation: interactive, `-p` and Agent SDK turns plus inline helpers | `"5m"` or `"1h"`, default unset; v2.1.242+ [EXT:https://code.claude.com/docs/en/settings-reference] |
| `subagentPromptCacheTtl` | Settings, any file | Subagents, workflows, and Claude Code's background and helper requests such as compaction and session titles | `"5m"` or `"1h"`, default unset; v2.1.242+ [EXT:https://code.claude.com/docs/en/settings-reference] |
| `CLAUDE_CODE_PROMPT_CACHE_TTL` | Environment | Main conversation | `5m` or `1h`; beats `promptCacheTtl` and `ENABLE_PROMPT_CACHING_1H`, and `FORCE_PROMPT_CACHING_5M` overrides it; v2.1.242+ [EXT:https://code.claude.com/docs/en/env-vars] |
| `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` | Environment | Requests outside the main conversation (subagents, workflows, background work) | `5m` or `1h`; beats `subagentPromptCacheTtl` and `ENABLE_PROMPT_CACHING_1H`, and `FORCE_PROMPT_CACHING_5M` overrides it; v2.1.242+ [EXT:https://code.claude.com/docs/en/env-vars] |
| `experimental.cacheTtl` | Subagent file frontmatter, inside the `experimental` map, not at top level (plugin agents support it too) | That subagent's requests | `5m` or `1h`; `1h` ignored while a subscription uses usage credits; read only from subagent files; v2.1.248+ [EXT:https://code.claude.com/docs/en/sub-agents] [EXT:https://code.claude.com/docs/en/plugins/components] |
| `ENABLE_PROMPT_CACHING_1H=1` | Environment (shell, container, or SDK `options.env`) | Every request in both buckets | Intended for API key, Bedrock, Agent Platform, Foundry and Claude Platform on AWS users; subscription users on usage credits can set it to keep one hour [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/agent-sdk/cost-tracking] |
| `FORCE_PROMPT_CACHING_5M=1` | Environment | Both buckets | Forces five minutes, overriding every other TTL control [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/prompt-caching] |

- The two settings, the two bucket environment variables and the frontmatter `cacheTtl` each take only `5m` or `1h` and ignore other values. [EXT:https://code.claude.com/docs/en/prompt-caching] [EXT:https://code.claude.com/docs/en/sub-agents] When several controls apply, the first match wins: `FORCE_PROMPT_CACHING_5M=1`, the bucket's environment variable, the bucket's setting, a subagent's frontmatter `cacheTtl` (subagent requests only), `ENABLE_PROMPT_CACHING_1H=1`, then the bucket default. [EXT:https://code.claude.com/docs/en/prompt-caching]
- With an API key or cloud provider, `promptCacheTtl: "1h"` gives only the main conversation an hour; the other bucket keeps five minutes until it gets its own TTL, so set both keys to cover every request. [EXT:https://code.claude.com/docs/en/prompt-caching] [EXT:https://code.claude.com/docs/en/settings-reference]
- `promptCacheTtl: "1h"` keeps the one-hour cache on the main conversation while drawing on usage credits. [EXT:https://code.claude.com/docs/en/agent-sdk/cost-tracking]
- `--agents` JSON definitions, including the `-p` file form, ignore `experimental`, and the field is read only from subagent files. [EXT:https://code.claude.com/docs/en/sub-agents]
- The docs suggest `FORCE_PROMPT_CACHING_5M=1` when debugging cache behavior, comparing the two TTLs, or overriding a longer TTL set in managed settings. [EXT:https://code.claude.com/docs/en/prompt-caching]
- The API bills each one-hour cache write at a higher rate than a five-minute one, and in the managed `modelPricing` key an `overrides` row's single `cacheWrite` rate covers both five-minute and one-hour writes. [EXT:https://code.claude.com/docs/en/settings-reference]
- `DISABLE_PROMPT_CACHING=1` disables caching for all models and takes precedence over the per-model variables; `DISABLE_PROMPT_CACHING_FABLE=1` covers Fable models. [EXT:https://code.claude.com/docs/en/env-vars]
- `DISABLE_PROMPT_CACHING_SONNET` and `DISABLE_PROMPT_CACHING_OPUS` cover only the model the `sonnet` or `opus` alias resolves to, so another pinned ID keeps caching; `DISABLE_PROMPT_CACHING_HAIKU` covers the default Haiku model wherever it runs (the main conversation from v2.1.283) and a differing background model set with the deprecated `ANTHROPIC_SMALL_FAST_MODEL`. [EXT:https://code.claude.com/docs/en/prompt-caching]
- The disable and TTL variables can be set organization-wide in the `env` block of managed settings. [EXT:https://code.claude.com/docs/en/prompt-caching]

## What breaks the cache

- The cache matches the request prefix exactly, so a change anywhere recomputes everything after it; there is no per-file or per-segment caching. The layers, in order, are the system prompt (core instructions, tool definitions), project context (CLAUDE.md, auto memory, unscoped rules) and the conversation. [EXT:https://code.claude.com/docs/en/prompt-caching]

| Action | Effect on the next request |
|--------|----------------------------|
| Switching models: `/model`, a skill or command whose frontmatter `model` differs from the session model, `opusplan` plan-mode toggles, automatic model fallback on Fable models, Opus 5.5, Sonnet 5.5 and Opus 5 | Reads the whole history with no cache hits, since each model has its own cache [EXT:https://code.claude.com/docs/en/prompt-caching] |
| A `fallbackModel` switch | One turn with a cold cache on the fallback model [EXT:https://code.claude.com/docs/en/settings-reference] |
| Changing effort | No cache hits on most models; kept with an API key or Claude subscription on Fable 5.1 and later (Fable 5.1 from v2.1.260), Opus 5.5, Sonnet 5.5 and Haiku 5.5, but not on Bedrock, Agent Platform, a Claude apps gateway, with `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` set, or under a HIPAA configuration [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Fast mode on or off, including Claude Code's own fallback to standard speed after a rate limit | Can't use what the other speed cached [EXT:https://code.claude.com/docs/en/prompt-caching] |
| A change in the set of tool definitions | Invalidates, except toggling `/advisor`; when tool search defers MCP tools (the default on supported models) the first request's tool list is kept, so servers connecting or disconnecting don't disturb the cache [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Without tool search: a server connects or a dynamic update adds tools, or a tool is removed on purpose | Invalidates; a server dropping out on its own keeps the cache, and a remote server's automatic reconnect keeps it unless a request adds `WaitForMcpServers`, which invalidates once [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Deny rule in the tool-name position (bare name, `Bash(*)`, `"*"`, `"mcp__*"`) | Invalidates, and so does removing it, only when tool search is unavailable or disabled; scoped deny rules and all allow and ask rules never change the tool set [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Plugin changes | Skills, commands, agents, hooks, monitors and themes never invalidate; plugin MCP servers follow the MCP rules; in `-p`, `/reload-plugins` (v2.1.260+) leaves plugin MCP changes to the next session [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Compaction | Invalidates the conversation layer and rebuilds project context; after a break longer than the TTL the summarization request is uncached [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Dropping a batch of old images or PDFs at the request limits | Reprocesses from the earliest affected message [EXT:https://code.claude.com/docs/en/prompt-caching] |
| Upgrading Claude Code | A new version typically updates the system prompt or tool definitions, so the first conversation started after the upgrade builds its cache from the top; auto-update applies on next launch, never mid-session, and `DISABLE_AUTOUPDATER=1` lets you control when upgrades apply [EXT:https://code.claude.com/docs/en/prompt-caching] |
| A gateway that strips `cache_control` markers while returning success | Whole history bills as uncached input every turn; when a gateway rejects them with a `400` naming `cache_control`, Claude Code moves the marker off the mid-conversation system-context block onto the last conversation message until it exits, so that block bills uncached and the conversation stays cached [EXT:https://code.claude.com/docs/en/prompt-caching] |
| `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` set | Mid-conversation system context such as file-change notices is sent uncached [EXT:https://code.claude.com/docs/en/prompt-caching] |

- Kept: editing repository files Claude already read, editing project-root or user CLAUDE.md mid-session (read at start and held until `/clear`, `/compact` or restart), changing permission mode (except plan mode under `opusplan`), changing output style, invoking skills and commands (unless the frontmatter names a different `model`), `/recap`, `/rewind`, and spawning a subagent. [EXT:https://code.claude.com/docs/en/prompt-caching]
- Resume re-sends the whole conversation and reads from cache only the unchanged prefix still within the TTL. By default the resumed conversation keeps the system prompt it started with and switches to the current prompt at its first compaction, rebuilding that layer once. [EXT:https://code.claude.com/docs/en/prompt-caching] In bare mode (`--bare` or `CLAUDE_CODE_SIMPLE=1`) outside cloud sessions the prompt isn't recorded unless `--system-prompt-snapshot on` is passed, and `--system-prompt-snapshot off` (v2.1.257+) rebuilds it on every request. [EXT:https://code.claude.com/docs/en/cli-reference] Resume: [Sessions](sessions-and-results.md#resume-and-continue).
- The cache is effectively scoped to one machine and directory: the system prompt embeds the auto memory paths and the conversation opens with the working directory, platform, shell and OS version, so sessions in different directories miss each other's cache. Parallel sessions in the same directory can share it, and sequential ones only when the startup git status snapshot (branch, recent commits) matches. [EXT:https://code.claude.com/docs/en/prompt-caching]
- At the API level caches are isolated per organization (on some providers per workspace), and two requests share a cache only when model, speed and prefix match. [EXT:https://code.claude.com/docs/en/prompt-caching]
- `--exclude-dynamic-system-prompt-sections` moves per-user context such as the auto memory location into the first user message to improve reuse across users and machines; it applies only with the default system prompt (ignored with `--system-prompt` or `--system-prompt-file`) and is for use with `-p` in scripted, multi-user workloads. [EXT:https://code.claude.com/docs/en/cli-reference]
- A line containing only `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` in replacement prompt text splits it so the part above stays cached (v2.1.275+, in the configurations the Agent SDK system-prompt page lists). [EXT:https://code.claude.com/docs/en/cli-reference]
- A subagent other than a fork warms its own cache instead of reading the parent's, which stays intact; a fork reads the parent's cache, and a resumed subagent can read the cache the original run warmed. [EXT:https://code.claude.com/docs/en/prompt-caching]
- Workflow agents in one run with the same model, effort, agent type, tools, output schema and working directory share a prefix, and one that starts after a matching sibling's response has begun reads its cache. When a fan-out starts several matching agents, Claude Code holds all but the first for up to `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS` (default `5000`, `0` disables, no wait when `DISABLE_PROMPT_CACHING` is set, v2.1.229+). [EXT:https://code.claude.com/docs/en/workflows] [EXT:https://code.claude.com/docs/en/env-vars]
- Idle compaction is on by default only in interactive terminal sessions, the VS Code chat panel and local or SSH Code tab sessions, for a conversation on the one-hour TTL with `autoCompactEnabled` on, context at the threshold (default 200,000, set by `CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`) and about an hour idle with the computer awake; `idleCompaction: false` (v2.1.290+) or `DISABLE_AUTO_COMPACT` turns it off. [EXT:https://code.claude.com/docs/en/settings-reference] [EXT:https://code.claude.com/docs/en/env-vars]

## Observing cache use

- `claude -p "hello" --output-format json` reports the TTL of main-conversation cache writes under `usage.cache_creation`: `ephemeral_1h_input_tokens` or `ephemeral_5m_input_tokens`. [EXT:https://code.claude.com/docs/en/prompt-caching] Result fields: [Sessions and results](sessions-and-results.md).
- Every response reports `cache_creation_input_tokens` (written, at the cache-write rate) and `cache_read_input_tokens` (served from cache, below the standard input rate), which a status line script reads live from `current_usage`. A high read-to-creation ratio means caching works; creation staying high turn after turn means the prefix keeps changing. [EXT:https://code.claude.com/docs/en/prompt-caching]
- After the main conversation's first response, `/usage` adds a `Prompt cache (main)` line (v2.1.251+): request count, share of input tokens from cache, misses, expected rebuilds after compaction or tool-result clearing, and warm or cold with the TTL in effect, or `no prompt caching reported by the API`. It covers the main conversation only, not subagents, and works on every provider and gateway. [EXT:https://code.claude.com/docs/en/costs]
- The line names the likely cause of the last miss when Claude Code can identify one (v2.1.260+), and a status line script reads the same numbers from the `prompt_cache` object (v2.1.251+). [EXT:https://code.claude.com/docs/en/prompt-caching]
- SessionStart hooks on a `resume` or `fork` whose transcript has at least one response get `seconds_since_last_response`, `context_tokens`, `prompt_cache_likely_expired` and `estimated_cache_write_usd` (v2.1.251+). [EXT:https://code.claude.com/docs/en/hooks]
- PreModelSwitch hook input carries `prompt_cache_warm`, `cache_ttl` (`"5m"` or `"1h"`) and `estimated_cache_write_usd`, priced on `to_model` at the `cache_ttl` rate. [EXT:https://code.claude.com/docs/en/hooks]
- A PostToolUse hook on a foreground Agent call gets `tool_response.usage`, including both cache token fields, for the subagent's final request only; a background launch, or a foreground task moved to the background mid-run (`status: "async_launched"`), carries no usage fields, and rollups across subagents use the token counters filtered to `query_source` `"subagent"`. [EXT:https://code.claude.com/docs/en/hooks]
- In the Agent SDK result, `usage` counts only the top-level loop, while `total_cost_usd` and `modelUsage` include subagents. [EXT:https://code.claude.com/docs/en/agent-sdk/cost-tracking]
- The OpenTelemetry exporter reports cache read and creation tokens per user and session. [EXT:https://code.claude.com/docs/en/prompt-caching]
