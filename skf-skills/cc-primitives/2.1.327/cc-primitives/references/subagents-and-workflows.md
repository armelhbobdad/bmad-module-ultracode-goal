## Subagent definitions

- Each subagent has its own context window, system prompt, tools and permissions; it gets its own system prompt plus basic environment details, not the Claude Code system prompt. [EXT:https://code.claude.com/docs/en/sub-agents]
- Priority: managed (1), `--agents` JSON (2, session only), `.claude/agents/` (3, walked up from the working directory), `~/.claude/agents/` (4), plugin `agents/` (5); identity comes from the `name` field. [EXT:https://code.claude.com/docs/en/sub-agents]
- Frontmatter: `name`, `description` required; `tools` (allowlist, default inherit), `disallowedTools` (applied first), `model` (`sonnet`, `opus`, `haiku`, `fable`, full ID or `inherit`), `permissionMode`, `maxTurns`, `autoCompactWindow` (v2.1.296+), `skills` (preloaded), `mcpServers`, `hooks`, `memory` (`user`/`project`/`local`), `background`, `omitClaudeMd`, `effort`, `isolation: worktree` (a temporary git worktree branched by default from your default branch, not the parent session's `HEAD`, and cleaned up when the subagent makes no changes; base branch and cleanup rules: [Worktrees and background sessions](worktrees-and-background.md)), `color`, `initialPrompt`, and `experimental.cacheTtl` (`5m` or `1h` prompt cache lifetime, v2.1.248+, read only from subagent files, with `1h` ignored while a Claude subscription is using usage credits; see [Limits and caching](limits-and-caching.md)). Plugin subagents ignore `permissionMode`, `mcpServers`, `hooks` and `initialPrompt`. [EXT:https://code.claude.com/docs/en/sub-agents]
- In `--agents` JSON each key is an agent name; `prompt` is the system prompt. [EXT:https://code.claude.com/docs/en/sub-agents]
- Unset `permissionMode` inherits the main conversation's mode. When the main conversation is in `bypassPermissions`, `acceptEdits` or `auto`, the subagent runs in that same mode and its `permissionMode` is ignored. Under `plan` the subagent stays in plan mode whatever it sets (agent team teammates follow the agent teams rules), and a `dontAsk` setting there denies what plan mode would ask about. Under `default` or `dontAsk` the subagent's mode applies, except that it keeps the main conversation's mode when it sets `bypassPermissions` (v2.1.267+) or sets `auto` while auto mode isn't available to it. [EXT:https://code.claude.com/docs/en/sub-agents]
- Omit `Agent` from `tools` (or add it to `disallowedTools`) to stop a subagent spawning subagents. Every non-fork subagent loses `AskUserQuestion`, `EndConversation`, `EnterPlanMode`, `ScheduleWakeup`, `WaitForMcpServers` and `Workflow` even when they are listed in `tools`. It also loses `Agent` at the depth limit and `ExitPlanMode` unless `permissionMode` is `plan`. Background subagents (the default) keep only a smaller built-in set. Forks skip both filters and get their parent conversation's exact tool pool (a fork at the depth limit keeps `Agent` listed, but the tool returns an error instead of spawning). [EXT:https://code.claude.com/docs/en/sub-agents]

## Delegation and execution

- Claude delegates by `description`; an @-mention tells Claude to run the named subagent for one task (Claude still writes its task prompt from your full message); `claude --agent <name>` makes the main thread that agent. [EXT:https://code.claude.com/docs/en/sub-agents]
- Foreground subagents block; with nothing configured, subagents Claude spawns from the main conversation start in the background and report via a completion notification. Fork mode is on by default from v2.1.302 (interactive terminal from v2.1.232). While it is on, Claude can't wait for a subagent in interactive terminal, VS Code or desktop sessions on your machine; it can in `-p` and Agent SDK runs. `CLAUDE_CODE_FORK_SUBAGENT=0` turns fork mode off, and `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` instead makes Claude wait for every subagent and turns background tasks off. [EXT:https://code.claude.com/docs/en/sub-agents]
- Non-fork subagents start with no conversation history, but their initial context holds every level of the `CLAUDE.md` hierarchy the main conversation loads. The built-in Explore and Plan subagents skip it, and a subagent with `omitClaudeMd` loads only the managed policy files (none when the definition comes from managed settings). For these, a subdirectory's `CLAUDE.md` and matching path-scoped rules still load when they work with files there; restate any rule that must reach them in the delegation prompt. A fork inherits the conversation but cannot fork again. [EXT:https://code.claude.com/docs/en/sub-agents]
- Resume with SendMessage by agent ID or name; Explore and Plan are one-shot. [EXT:https://code.claude.com/docs/en/sub-agents]
- No agent message counts as user approval. [EXT:https://code.claude.com/docs/en/sub-agents]
- Transcripts: `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`. [EXT:https://code.claude.com/docs/en/sub-agents]
- Disable one with `permissions.deny` `Agent(subagent-name)`; Stop hooks in frontmatter become SubagentStop. [EXT:https://code.claude.com/docs/en/sub-agents]

## Limits

- Nesting up to three layers (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, `1` disables); 20 concurrent (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, v2.1.217+; ultracode exempt; workflow agents and agent team teammates follow their own limits); no total limit; startup warning over 15,000 tokens of descriptions. [EXT:https://code.claude.com/docs/en/sub-agents]
- `CLAUDE_CODE_SUBAGENT_MODEL` plus `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257+) runs every subagent, teammate and workflow agent on that model, ignoring `model` fields and per-invocation models, except that a fork and a skill that runs in a subagent with `model: inherit` keep their parent conversation's model. `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` alone runs subagents on the main conversation's model, except the built-in Explore subagent, which keeps its listed model. [EXT:https://code.claude.com/docs/en/sub-agents]

## Dynamic workflows

- A JavaScript script, written by Claude, that orchestrates many subagents in the background; only the final answer returns to Claude's context. [EXT:https://code.claude.com/docs/en/workflows]
- Opt in with the keyword `ultracode` in a prompt you type (the keyword does not start a workflow from a `-p` prompt, an Agent SDK prompt not stamped as human input, a scheduled task prompt, or a relayed webhook payload or pull request comment), or with a direct request such as "use a workflow", which Claude treats as the same opt-in; `/effort ultracode`, `claude --effort ultracode` (which also sets effort `xhigh`) or the `ultracode` setting turn on ultracode, where Claude plans a workflow for each substantive task; Pro plans turn workflows on in `/config`. Workflows themselves run under `claude -p` and the Agent SDK, where the launch must pass permission evaluation (see Permissions below). [EXT:https://code.claude.com/docs/en/workflows]
- `/workflows` lists runs; saved workflows live in `.claude/workflows/` or `~/.claude/workflows/` and read `args`. [EXT:https://code.claude.com/docs/en/workflows]
- Script API: `meta` first (literal with `name`, `description`), `agent()` (optionally with `schema`), `parallel()`, `pipeline()`, `phase()`, `log()`; `meta.phases` titles must match `phase()` calls. [EXT:https://code.claude.com/docs/en/workflows]
- `agent()` resolves to `null` when you stop it mid-run or when it hits an unrecoverable API error. The call fails with an error when the output still fails schema validation after five attempts (`MAX_STRUCTURED_OUTPUT_RETRIES`), on a provably contradictory schema, or when its sixth attempt stalls (at most five restarts, counting any restart you ask for with `r`; the error starts `agent stalled on all 6 attempts`, `agent lost its reply on all 6 attempts` or `agent abandoned after 6 attempts`). To give a silent agent more time, pass `stallMs` (milliseconds) on the call or set `CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS` (which also applies to subagents outside workflows). Lengthening the stall window does not help `agent lost its reply`, because a streaming idle watchdog ended the response first; `CLAUDE_STREAM_IDLE_TIMEOUT_MS` sets that watchdog's timeout. Inside `parallel()`/`pipeline()` a stalled agent's slot holds `null`; awaited directly, the error ends the run. [EXT:https://code.claude.com/docs/en/workflows]
- Permissions: workflow agents get normal checks and the subagent permission-mode rules. In auto mode the launch prompt shows on the first launch only (any Yes records consent in user settings; skipped entirely with ultracode on); in manual and `acceptEdits` mode it shows on every run unless you chose `Yes, and don't ask again` for that workflow in this project (offered only for a bundled, saved or plugin workflow run by name); under `bypassPermissions` it never shows. In `-p`/SDK no prompt shows, but the `Workflow` call goes through normal permission evaluation (deny rules, ask rules and `dontAsk` apply); let it start with an allow rule `Workflow` (every workflow) or `Workflow(<name>)` (one saved workflow by name), auto mode, `bypassPermissions`, a `PreToolUse` hook returning `allow` (not enough on its own in plan mode), or `--permission-prompt-tool`/`canUseTool`. [EXT:https://code.claude.com/docs/en/workflows]
- Resume: a paused run resumes from `/workflows` (select it, press `p`); for a stopped run, Claude relaunches the same script, and Claude Code refuses the relaunch until the stopped run's agents have exited. A relaunch replays agents in start order. Completed agents return their saved results up to the first agent whose prompt changed (an edited script or a different earlier result), which runs again along with every agent after it. Agents still running when the run stopped start over; stopping the whole run fails no agent. A failed agent, including one stopped alone with `x`, runs again along with every agent the script starts after it, even completed ones. An agent that failed at a usage limit (v2.1.318+) runs again while completed agents return their saved results, unless the script called another agent after the failure and that agent returned a result: then every agent started after the failed one also runs again. Runs are resumable within the same session, including one resumed with `claude --resume`; a backgrounded or exited session does not continue a run until Claude relaunches it with a `Workflow` call, a fresh session starts the workflow over, and a relaunch that finds no saved results fails with `nothing to resume`. [EXT:https://code.claude.com/docs/en/workflows]

## Workflow limits and cost

- No mid-run user input (a run pauses on its own only for agent permission prompts and a usage-limit wait), no direct filesystem/shell access, no `import()`, and no `Date.now()`/`Math.random()`/no-argument `new Date()` (they throw). [EXT:https://code.claude.com/docs/en/workflows]
- The usage-limit pause (v2.1.271+, v2.1.319+ in the Desktop Code tab) happens only when all of these hold: a claude.ai subscription without usage-based billing; an interactive terminal session or a local session started in the Code tab (not an SSH, WSL, Dispatch or scheduled task session, one started from Remote Control or through a corporate launcher, or one with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` set); `autoContinueAtUsageLimit` on; in the Code tab, the `Auto-continue when limits reset` checkbox checked (the default; unchecked, Code tab runs stop pausing unless managed settings set `autoContinueAtUsageLimit` to `true`); a limit that resets within 24 hours; and a run that hasn't already waited twice. When one doesn't hold the agent fails at the limit instead, as it does under `claude -p`, the Agent SDK, a background session, or a Remote Control or agent team teammate session, so relaunch the workflow after the reset (see [Limits and caching](limits-and-caching.md)). [EXT:https://code.claude.com/docs/en/workflows]
- Under `claude -p`, after Claude's turn ends and stdin has closed, the run stays open for a running workflow until it finishes or the 10-minute cap ends the wait: unless a background command the main conversation started is still running, Claude Code stops whatever is still running after 10 minutes of continuous idle waiting by default and drops its partial result. Set `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` to change the cap, or to `0` to wait without one. [EXT:https://code.claude.com/docs/en/headless]
- Up to 16 concurrent agents by default, fewer when fewer CPUs are available, including in a CPU-limited container (`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`, `1` to `256`, v2.1.269+), and in a fan-out the agents that share the first agent's prompt-cache prefix are held until its response begins, for at most `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS` (`5000` ms by default; `0` disables the hold); see [Limits and caching](limits-and-caching.md). [EXT:https://code.claude.com/docs/en/workflows]
- A workflow agent's requests fall outside the main conversation's cache TTL bucket, so its prompt cache holds five minutes by default, even on a Claude subscription; `subagentPromptCacheTtl` set to `1h` keeps it an hour, and the API bills 1-hour cache writes at a higher rate; see [Limits and caching](limits-and-caching.md). [EXT:https://code.claude.com/docs/en/workflows]
- At most 4,096 items per `parallel()`/`pipeline()` call and 1,000 agents per run. [EXT:https://code.claude.com/docs/en/workflows]
- An advisory `Large workflow` warning appears above 25 agents (a chosen size guideline's count replaces 25) or 1.5M projected tokens, and is not shown with ultracode on. [EXT:https://code.claude.com/docs/en/workflows]
- `disableWorkflows` / `CLAUDE_CODE_DISABLE_WORKFLOWS=1` turn workflows off. [EXT:https://code.claude.com/docs/en/workflows]
