## claude --worktree

- `claude --worktree <name>` (`-w`) creates a worktree under `.claude/worktrees/<name>/` at the repository root, on a new branch named `worktree-<name>` by default, and starts Claude at the worktree's root; with no name Claude Code generates one such as `bright-running-fox`. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/cli-reference]
- Default creation branches from the repository's default branch (see [Base branch](#base-branch-worktreebaseref)) and checks out only tracked files; the docs advise adding `.claude/worktrees/` to `.gitignore` so worktree contents don't appear as untracked files in the main checkout. [EXT:https://code.claude.com/docs/en/worktrees]
- Interactive runs need workspace trust, but `claude -p --worktree` skips the trust check; `--worktree` passed in a directory that isn't a git checkout, with no `WorktreeCreate` hook active, fails with `Can only use --worktree in a git repository`. [EXT:https://code.claude.com/docs/en/worktrees]
- `--tmux` creates a tmux session for the worktree and requires `--worktree`; it uses iTerm2 native panes when available, and `--tmux=classic` forces traditional tmux. [EXT:https://code.claude.com/docs/en/cli-reference]
- PR form: `--worktree "#<number>"` (quoted so the shell doesn't read `#` as a comment), a GitHub pull request URL or a GitLab merge request URL fetches that change's head commit from `origin` into `.claude/worktrees/pr-<number>` (branching from a GitLab merge request needs v2.1.233+); only the number is read, and the fetch path is `pull/<number>/head` on github.com, `merge-requests/<number>/head` on gitlab.com, and both in that order on any other host. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/cli-reference]
- The PR/MR fetch never waits for input: if git or ssh would ask for a password, a key passphrase or a new SSH host confirmation, Claude Code exits with `Error creating worktree: Failed to fetch PR/MR #<number>`; a key held by `ssh-agent` still works, and one manual `git fetch` records a new host beforehand. [EXT:https://code.claude.com/docs/en/worktrees]
- Creation is refused when `.claude`, `.claude/worktrees` or the worktree directory is a symlink; checkout runs with `GIT_NO_REPLACE_OBJECTS=1` and skips the repository's own filter drivers, so `git lfs install --local` leaves LFS pointer files until `git lfs pull` (the drivers ran before v2.1.247); four filter-driver config cases stop creation, and so does a partial clone in which Claude Code couldn't fetch every git object the starting commit needs (`This repository is a partial clone`). [EXT:https://code.claude.com/docs/en/worktrees]
- An existing `--worktree` name is opened instead of created (`belongs to a different repository` or `is a leftover worktree` means git ties that directory elsewhere: pass a different name); with the default `"fresh"` base it resets to the default branch only when all hold: the sandbox isn't restricting writes and neither checkout's `.claude` settings enable it, no uncommitted or untracked files, still on its own branch, and no commits of its own or its PR/MR merged with the remote branch deleted (detected from git state alone). [EXT:https://code.claude.com/docs/en/worktrees]
- In every other case, including an unverifiable state, `worktree.baseRef` `"head"` or a PR/MR name, the worktree reopens at its old tip (with the sandbox, run `git fetch origin` and pass a new name). [EXT:https://code.claude.com/docs/en/worktrees]
- Interactive exit checks for changed or untracked files, uncommitted work in checked-out submodules and new commits: a clean unnamed session's worktree and branch are removed automatically, a named session prompts first, a worktree with work prompts keep or remove (keeping prints a `claude --worktree <name> --resume` command), a worktree on another branch with commits past the starting commit prompts and either answer keeps that other branch and its commits, and an unverifiable state prompts; these rules cover only worktrees Claude created with git. [EXT:https://code.claude.com/docs/en/worktrees]
- A `-p` run has no exit prompt, so Claude Code doesn't clean up its worktree and leaves the lock it took at creation until a later session's stale-lock sweep releases it; remove it with `git worktree remove`, running `git worktree unlock` first if git refuses. [EXT:https://code.claude.com/docs/en/worktrees]
- Resuming a session that ended inside a worktree without exiting it returns it to that worktree, for interactive resumes, `--continue` and `--resume` with `-p`, and the Agent SDK (before v2.1.212 a non-interactive resume stayed in the starting directory); `--continue` picks the most recent session recorded under the launch directory. [EXT:https://code.claude.com/docs/en/worktrees]
- Resume from the main checkout or another directory of the repository: a worktree Claude created with git under `.claude/worktrees/` is re-entered even from inside it, but from inside any other worktree Claude Code re-enters only one it can vouch for from there, and declines one that is its own repository, one without git metadata, or a launch from a subdirectory of a `git worktree add` worktree. [EXT:https://code.claude.com/docs/en/worktrees]
- Before re-entering, Claude Code verifies the worktree is still a checkout separate from the main one (the `Refusing to use <path> as an isolation worktree` check also runs on create and reuse); `--fork-session` starts in the launch directory and leaves the original worktree untouched; a deleted worktree resumes in the launch directory and clears the binding; the transcript follows Claude into and out of a git-created worktree, while a hook-created one keeps it at the launch directory. [EXT:https://code.claude.com/docs/en/worktrees]
- `--resume <session-id>` searches the current project directory and its git worktrees, then every other project on the machine (before v2.1.223, only the project and its worktrees). [EXT:https://code.claude.com/docs/en/cli-reference] See [Sessions](sessions-and-results.md#resume-and-continue).
- Under `-p` and Agent SDK resumes, every refusal except a gone worktree (which prints `Notice: the worktree <path> for this session no longer exists...` and continues) stops the resume with a stderr error instead of continuing without isolation; with `--output-format stream-json` it also arrives on stdout as a `result` message with subtype `error_during_execution` and the text in `errors` (v2.1.260+). [EXT:https://code.claude.com/docs/en/worktrees]

| stderr error | Meaning | `startup_failure_reason` (v2.1.274+) |
|---|---|---|
| `Error: cannot resume into worktree <path>: ...` | Refused as unsafe; the binding is cleared before exit, so the next resume continues in the current directory without isolation (before v2.1.260 every retry failed the same way) | `worktree_resume_refused` [EXT:https://code.claude.com/docs/en/worktrees] |
| `Error: could not verify worktree <path> for this resume, so the resume was aborted...` | Resume aborted | `worktree_unverified` [EXT:https://code.claude.com/docs/en/worktrees] |
| `Error: ...The worktree binding is kept.` | Couldn't vouch for the worktree from the launch directory; binding kept | `worktree_resume_refused` [EXT:https://code.claude.com/docs/en/worktrees] |

With transcript writes suppressed, the binding clear can't be saved, so the same command is refused again, and the error names `--fork-session` or a new conversation as ways to continue. [EXT:https://code.claude.com/docs/en/worktrees]

## Base branch: worktree.baseRef

- `"fresh"` (default) branches from `origin/<default-branch>` (usually `main`); `"head"` branches from the current local `HEAD`, carrying unpushed commits and feature-branch state, and inside a linked worktree resolves to that worktree's `HEAD`, not the main checkout's. [EXT:https://code.claude.com/docs/en/settings-reference] [EXT:https://code.claude.com/docs/en/worktrees]
- The `worktree` object applies to `--worktree`, the `EnterWorktree` tool, isolated subagents and background sessions, and may be set in any settings file. [EXT:https://code.claude.com/docs/en/settings-reference]
- `worktree.baseRef` can't be a branch name: to start from a specific existing branch, or place the worktree outside the repository, create it with `git worktree add` and start Claude inside it. [EXT:https://code.claude.com/docs/en/worktrees]
- For `"fresh"`, when the repository hasn't been fetched in the last 24 hours Claude Code fetches the default branch (capped at five seconds) and uses the cached ref if the fetch fails; the fetch never waits for terminal input and counts as failed when git or ssh would prompt; with no remote, or `origin/HEAD` neither cached nor fetchable, it falls back to the current local `HEAD`. [EXT:https://code.claude.com/docs/en/worktrees]

## .worktreeinclude

- A `.worktreeinclude` file at the project root, in `.gitignore` syntax, copies files that match a pattern and are also gitignored (such as `.env`) into every worktree Claude Code creates with git (`--worktree`, subagent and desktop-app parallel-session worktrees); tracked files are never copied. [EXT:https://code.claude.com/docs/en/worktrees]
- A `**/` pattern copies out of a wholly ignored directory only when that directory matches or the first name after `**/` is in its path, so otherwise name the directory (`vendor/**/config.json`, not `**/config.json`); before v2.1.239 only a matching directory counted. [EXT:https://code.claude.com/docs/en/worktrees]
- With a `WorktreeCreate` hook configured, `.worktreeinclude` is not processed; copy local configuration files such as `.env` inside the hook script instead. [EXT:https://code.claude.com/docs/en/hooks] [EXT:https://code.claude.com/docs/en/worktrees]

## Isolation checks

The checks cover a session started with `--worktree`, one that entered a worktree with `EnterWorktree`, a resumed worktree session, and every subagent such a session spawns (including subagents without `isolation: worktree`), whether interactive or background. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/sub-agents]

| Check | Blocks |
|---|---|
| File edits | `Edit`, `Write` or `NotebookEdit` targeting a path in the main checkout [EXT:https://code.claude.com/docs/en/worktrees] |
| Command working directory | A Bash, PowerShell or Monitor command whose working directory resolves to the main checkout, or can't be verified to stay outside it [EXT:https://code.claude.com/docs/en/worktrees] |
| Git redirects | A Bash or Monitor command redirecting git into the main checkout through `git -C`, `--git-dir`, `GIT_DIR`, `GIT_WORK_TREE` or a prior `cd` [EXT:https://code.claude.com/docs/en/worktrees] |
| Command shape | A Bash or Monitor command whose text can't be verified to keep any git inside the worktree (computed command name, unparseable syntax, `${!name}` or `${ command; }`); this check can't be turned off [EXT:https://code.claude.com/docs/en/worktrees] |

- The checks cover the repository Claude Code was launched from plus the main checkout a linked worktree is linked from (PowerShell gets only the working-directory check), and none tracks which files a shell command writes, so `cp` or a shell redirect into the main checkout without running git there isn't refused (permissions and sandboxing still apply). [EXT:https://code.claude.com/docs/en/worktrees]
- Claude sees each refusal as a tool error that names the worktree and says how to proceed; for a refused Bash, PowerShell or Monitor command the message contains `is isolated in the worktree <path>, but this command` plus the reason, such as a working directory that `resolved to the shared checkout` or `is in a different worktree`. [EXT:https://code.claude.com/docs/en/errors] [EXT:https://code.claude.com/docs/en/worktrees]
- `.claude` is a protected directory, with a few exceptions that include Claude's own git worktrees under `.claude/worktrees/`. [EXT:https://code.claude.com/docs/en/permission-modes]
- `EnterWorktree` to a path outside `.claude/worktrees/` prompts for approval (v2.1.206+; only `bypassPermissions` skips it, while a permission rule or "don't ask again" doesn't) and moves the working directory, write access and project configuration such as `CLAUDE.md` and settings; from inside a worktree session, or in a subagent with a pinned working directory such as `isolation: worktree`, only the `path` form is available and the target must be under `.claude/worktrees/` of the session's repository. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/tools-reference]
- `ExitWorktree` isn't available to subagents already in their own working directory such as `isolation: worktree`, and with `permissions.blockWritesOutsideWorkingDirectories` on (the key needs v2.1.314+) both worktree tools are removed or refused. [EXT:https://code.claude.com/docs/en/tools-reference] [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/settings-reference]

## What a worktree shares with the main checkout

The shared `.git`, project-scope plugins, saved Bash approvals and the skills, agents and commands read-through apply whether the worktree came from `--worktree` or `git worktree add`. [EXT:https://code.claude.com/docs/en/worktrees]

- Git commands in a worktree write to the main repository's shared `.git`; with the sandbox enabled, commands such as `git commit` work in a session at the worktree's root (where `--worktree` starts one) and by default fail with an `index.lock` error when `claude` runs in a subdirectory of the worktree; plugins installed at project scope from the main checkout also load in worktrees of the same repository. [EXT:https://code.claude.com/docs/en/worktrees] With `permissions.blockReadsOutsideWorkingDirectories` and sandboxing both on, the common `.git` stays readable and writable to sandboxed commands when the session's working directory is a linked worktree. [EXT:https://code.claude.com/docs/en/settings-reference]
- `.claude/settings.local.json` is read and written at the main checkout's root (v2.1.211+), so a "Yes, and don't ask again" Bash approval applies in the main checkout and every worktree and survives the worktree's removal; outside git, with a home-directory root, on Windows, or when the root or its `.git` or `.claude` entry isn't owned by the user, the file stays with the worktree. [EXT:https://code.claude.com/docs/en/settings] [EXT:https://code.claude.com/docs/en/worktrees]
- Skills: with no `.claude/skills` at the worktree root the main checkout's project skills load (v2.1.277+), a worktree with its own `.claude/skills` loads only that copy, the same read-through covers `.claude/agents` and `.claude/commands`, and skill discovery walks parent directories only up to the worktree root. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/skills]
- Paths in local settings rules anchor at the session's primary working directory, so in a worktree session `Edit(/src/**)` matches the worktree's own `src/`, and workspace trust is keyed on the main checkout's root. [EXT:https://code.claude.com/docs/en/permissions]
- Auto memory: all worktrees of a repository share `~/.claude/projects/<project>/memory/`, while a gitignored `CLAUDE.local.md` exists only in the worktree where it was created. [EXT:https://code.claude.com/docs/en/memory] See [Auto Memory](memory-and-settings.md#auto-memory).
- Hooks: after Claude enters a worktree mid-session, `${CLAUDE_PROJECT_DIR}` still points at the project root where the session started (so a hook command such as `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` still runs the main checkout's script) while the input `cwd` is the worktree root and follows `cd`; if the current directory no longer exists, command hooks run from the session's start directory, the project root, the home directory or the system temp directory, whichever exists first. [EXT:https://code.claude.com/docs/en/hooks] [EXT:https://code.claude.com/docs/en/worktrees] See [Hooks](hooks.md#handlers).
- Desktop-app worktree sessions read project configuration (settings, hooks, skills, agents, commands, `.mcp.json`) from the main checkout's root, run hooks there and point `${CLAUDE_PROJECT_DIR}` at it, while `CLAUDE.md` and `.claude/rules/` load from the worktree. [EXT:https://code.claude.com/docs/en/worktrees]

## Subagent and workflow agent worktrees

- `isolation: worktree` in a subagent's frontmatter, or `isolation: "worktree"` passed when spawning it (a fork spawned through the Agent tool can pass it too), gives it a temporary worktree with the same base as `--worktree`, removed automatically if the subagent finishes without changes and otherwise kept until the periodic sweep can remove it without losing work. [EXT:https://code.claude.com/docs/en/sub-agents] [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/worktrees]
- Its instruction files come from the main conversation, and in the default `.claude/worktrees/` location it doesn't load the worktree root's `CLAUDE.md` or `.claude/rules/` as it reads files there. [EXT:https://code.claude.com/docs/en/worktrees]
- It runs its Bash and PowerShell commands inside its worktree, and a command whose working directory resolves to the main checkout (for example after the worktree was removed mid-run) fails; the check covers the whole repository containing the launch directory and, for a session in a linked worktree, its main checkout. [EXT:https://code.claude.com/docs/en/sub-agents]
- `Agent(isolation:worktree)` in deny or ask rules matches Agent calls that request a git worktree; a parameter the model omits is never matched. [EXT:https://code.claude.com/docs/en/permissions]
- With `permissions.blockWritesOutsideWorkingDirectories` on, its file edits are refused when its worktree sits outside the working directories; add the repository's `.claude/worktrees` directory as a working directory. [EXT:https://code.claude.com/docs/en/settings-reference]
- The workflows page describes workflow agents only as working "in an isolated copy so edits don't conflict"; a workflow running an agent in its own worktree fires `WorktreeCreate`, and when a subagent or workflow agent finishes, its hook-created worktree is kept without running `WorktreeRemove`. [EXT:https://code.claude.com/docs/en/workflows] [EXT:https://code.claude.com/docs/en/hooks] See [Dynamic workflows](subagents-and-workflows.md#dynamic-workflows).
- Once its plan is approved, `/batch` spawns one background subagent per unit in an isolated worktree; it requires a git repository or a `WorktreeCreate` hook that creates the worktrees, and outside a git repository it needs v2.1.281+. [EXT:https://code.claude.com/docs/en/commands] [EXT:https://code.claude.com/docs/en/worktrees]

## Cleanup and locks

- A periodic sweep removes worktrees Claude created for subagents and background sessions (a backgrounded `--worktree` session's worktree included) once older than `cleanupPeriodDays` (default `30`, whole number, minimum `1`; `0` fails validation), following the retention sweep rules. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/settings-reference] The `cleanupPeriodDays` deletion runs as a background sweep after a session starts, as long as Claude Code can safely determine the retention period. [EXT:https://code.claude.com/docs/en/settings-reference]
- The sweep keeps a worktree that holds changed or untracked files or unpushed commits; has a checked-out submodule with changes, or submodules it can't inspect (v2.1.274+); hits one of the four filter-driver cases; belongs to a `--worktree` session not backgrounded (whatever its age); was created with `git worktree add` (even if a backgrounded `--worktree <name>` session ran in it); or lacks the marker Claude Code writes into the git metadata of worktrees it creates with git (hook-created worktrees included). [EXT:https://code.claude.com/docs/en/worktrees]
- Claude Code holds a `git worktree lock` on an agent's worktree while the agent runs (released when it finishes) and on the worktree it created for a backgrounded session while the session runs, so the sweep leaves it and `git worktree remove` refuses it; a session backgrounded with `←` or `/background` holds it from v2.1.248. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/agent-view]
- The sweep releases a lock Claude Code set for a session whose process has exited, never one set by hand; manual cleanup is `git worktree remove`, adding `--force` for uncommitted changes or untracked files, after `git worktree unlock` if a lock blocks it. [EXT:https://code.claude.com/docs/en/worktrees]

## WorktreeCreate and WorktreeRemove hooks

- `WorktreeCreate` replaces the default `git worktree` creation and fires in cases such as `claude --worktree`, `EnterWorktree` creating a worktree, an `isolation: "worktree"` subagent, a workflow agent in its own worktree, a background session's isolation, and `claude remote-control` in `worktree` mode. [EXT:https://code.claude.com/docs/en/hooks]
- It doesn't run for a worktree Claude adds with `git worktree add` through Bash (use a `PreToolUse` hook with the `Bash` matcher), and a plugin's hook doesn't run with `--worktree --tmux` because the worktree is created before plugins load (define it in a settings file; before v2.1.300 a plugin hook skipped `--worktree` alone too). [EXT:https://code.claude.com/docs/en/hooks]
- Both events have no matcher support, fire on every occurrence, and support `command`, `http` and `mcp_tool` hooks but not `prompt` or `agent`; `WorktreeCreate` input adds `name` (a user-given or generated slug) and `WorktreeRemove` input adds `worktree_path`. [EXT:https://code.claude.com/docs/en/hooks]
- A command hook prints the path as the last non-empty stdout line (ANSI escape codes are stripped; redirect any other output to stderr; a command hook can't return JSON), and an HTTP hook returns `hookSpecificOutput.worktreePath`; the path becomes the isolated session's working directory, and `systemMessage` and `continue` are discarded. [EXT:https://code.claude.com/docs/en/hooks]
- Any non-zero exit fails creation whatever the JSON says, as do a failed hook or no path; a relative path resolves against the directory the hook ran in, with `.` and `..` segments collapsed; a resulting path that isn't an enterable directory makes the session print an error naming it and exit with code 1; an absolute path with `.` or `..` segments, or any path through a symlink below the repository root, is refused. [EXT:https://code.claude.com/docs/en/hooks] [EXT:https://code.claude.com/docs/en/worktrees]
- A directory with no git metadata passes only when no git repository contains it (otherwise `git resolves its working tree to`), so create such directories outside any repository; outside a git repository, a failing hook lets a background session skip isolation and edit in place. [EXT:https://code.claude.com/docs/en/worktrees] [EXT:https://code.claude.com/docs/en/agent-view]
- `WorktreeRemove` fires only for hook-created worktrees: an interactive exit that removes it (prompted, or a clean unnamed session), a background-session delete, an `ExitWorktree` removal, and `claude remote-control` cleanups that find no changed or untracked files and no new commits. [EXT:https://code.claude.com/docs/en/hooks]
- Exit 0 counts as removed and nothing else is read, so the hook must delete the directory; non-zero fails the removal if the directory still exists (no git fallback); JSON output is discarded; Claude Code never deletes a hook-created worktree's branch, and it looks for changes only through git, so the hook must check a non-git worktree for work. [EXT:https://code.claude.com/docs/en/hooks]
- With no `WorktreeRemove` hook, an exit or `ExitWorktree` removes the returned path as `git worktree remove --force` would (a directory git doesn't recognize stays) and `claude remote-control` keeps it with `worktree removal failed, kept: <path>`; `ExitWorktree` refuses to remove a hook-created worktree unless the call passes `discard_changes: true`, with no prompt before the hook. [EXT:https://code.claude.com/docs/en/hooks]
- For a background-session delete, the stored path is verified first (symlinks refused), and the hook runs for a worktree that still holds files only when the delete is confirmed in agent view; `claude rm` keeps such a session and worktree. [EXT:https://code.claude.com/docs/en/hooks]

## Other worktree settings

The `worktree` object takes `baseRef`, `symlinkDirectories`, `sparsePaths` and `bgIsolation`, each settable in any settings file. [EXT:https://code.claude.com/docs/en/settings-reference]

| Key | Behaviour |
|---|---|
| `worktree.symlinkDirectories` | Repository-relative directories symlinked from the main repository into each worktree; default unset [EXT:https://code.claude.com/docs/en/settings-reference] |
| `worktree.sparsePaths` | Sparse-checks-out only the listed directories plus root-level files (default: whole tree); include `.claude` so each worktree has `.claude/settings.json` and `.claude/rules/`; while a sparse worktree exists git enables `extensions.worktreeConfig` in the shared `.git/config` [EXT:https://code.claude.com/docs/en/settings-reference] |
| `worktree.bgIsolation` | `"worktree"` (default) blocks `Edit` and `Write` in the main checkout until the background session calls `EnterWorktree`; `"none"` edits the working copy directly; a session moved to the background with `←` or `/background` edits in place regardless; added in v2.1.143 [EXT:https://code.claude.com/docs/en/settings-reference] [EXT:https://code.claude.com/docs/en/agent-view] |
| `worktree.location` | Only the desktop app reads it, for Desktop SSH sessions (user scope, in `~/.claude/settings.json` on the remote machine; Claude Desktop v1.44121.0+); `--worktree`, `EnterWorktree`, isolated subagents and background sessions ignore it [EXT:https://code.claude.com/docs/en/settings-reference] |

With `permissions.blockWritesOutsideWorkingDirectories` on, a background session can still edit when started with `claude --bg --worktree`, with `worktree.bgIsolation` set to `"none"`, or in a `git worktree add` worktree under the directory it started in. [EXT:https://code.claude.com/docs/en/worktrees]

## Background sessions

- Agent view, the background-session feature, is in research preview (introduced in v2.1.139), and its interface and keyboard shortcuts may change. [EXT:https://code.claude.com/docs/en/agent-view]
- `claude --bg "<prompt>"` (long form `--background`) starts a background session and returns immediately, printing `backgrounded · <short-id>` (plus ` · <name>` with `--name`) and the `claude agents`, `attach`, `logs` and `stop` commands, possibly after `Starting background service…`. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference]
- The prompt is positional: `--bg` with `-p` or `--print` is rejected before any session is created (`--bg and --print conflict`, v2.1.198+; earlier it silently created a job that could never be attached to). [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/errors]
- From v2.1.299, `--bg` is read as the flag only before any bare `--` and outside another flag's value; an ambiguous position starts nothing and exits 1 with `Couldn't tell whether --bg is a flag or text here`, so put `--bg` first. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/errors]
- `--bg` combines with `--name` (display name), `--model`, `--safe-mode` (customizations off), `--worktree`, `--agent <name>` (runs that subagent as the main agent; from v2.1.191 an unknown name is still reported as backgrounded but exits at once with `--agent '<name>' not found`) and `--exec '<cmd>'` (a PTY-backed shell job with no model, output kept only in memory, row cleaned up about five minutes after the command exits). [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/worktrees]
- `claude --resume <full-session-id> --bg` continues that session under its ID (v2.1.257+) or starts a copy under a new ID with a `note:` line; `--continue`, a bare `--resume`, or `--resume` with a name or path always starts a copy, and `--fork-session` starts one on purpose without the note. [EXT:https://code.claude.com/docs/en/agent-view]
- `--bg` and the commands that restart a session check workspace trust for the session's directory first (v2.1.281+); where no dialog can appear (a script, or a restart from another directory) they exit with `Workspace not trusted`, and for the home directory the variant `The home directory is trusted one session at a time` appears because home trust is never saved. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/errors]
- `disableAgentView: true` (any settings file, enforceable through managed settings) or `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` (for one session) turns off `claude agents`, `--bg`, `/background` and the on-demand supervisor, and whichever turns it off, the other can't turn it back on; a `claude agents` that prints a count followed by the configured subagents and exits means agent view is unavailable. [EXT:https://code.claude.com/docs/en/settings-reference] [EXT:https://code.claude.com/docs/en/env-vars] [EXT:https://code.claude.com/docs/en/agent-view]
- Resuming a still-running background session (v2.1.285+): `claude --resume <session>` attaches, and `claude -p --resume <session> "prompt"` typed at a terminal sends the prompt and attaches; with piped or redirected I/O, session-configuring, output-reading or run-limiting flags, or agent view off, it sends nothing and exits 1 printing `claude attach <id>` (or saying to find the session in `claude agents` when it can't determine the ID); `--fork-session` resumes a copy instead, `claude stop <id>` then the same command continues it with your flags, and `claude --continue` opens a finished background session (v2.1.257+) but not a running one. [EXT:https://code.claude.com/docs/en/sessions] See [Sessions](sessions-and-results.md#resume-and-continue).

## claude agents --json

`claude agents --json` is the supported way to read session state from outside Claude Code: poll `claude agents --json --all` and read each entry's `state`, `status` and `waitingFor`. [EXT:https://code.claude.com/docs/en/agent-view] It prints a JSON array and exits, listing every live session plus background sessions still `working` or `blocked` after their process exited; `--all` adds completed background sessions and `--cwd <path>` keeps sessions started under that directory. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] `claude agents --cwd` still lists a session that has moved into a worktree under that path, and `--add-dir` or `--mcp-config` placed before `agents` makes `--json` fail with `unknown option`. [EXT:https://code.claude.com/docs/en/agent-view]

| Field | Present | Meaning |
|---|---|---|
| `cwd`, `kind`, `startedAt` | Always | Working directory; `interactive` or `background`; start time in Unix milliseconds [EXT:https://code.claude.com/docs/en/agent-view] |
| `id` | Background sessions | Short ID for `claude attach`, `claude logs` and `claude stop`; also its directory name under `~/.claude/jobs/` [EXT:https://code.claude.com/docs/en/agent-view] |
| `state` | Background sessions | `working`, `blocked`, `done`, `failed` or `stopped` [EXT:https://code.claude.com/docs/en/agent-view] |
| `pid`, `status` | While the process is alive | Process ID; `busy`, `waiting` or `idle` [EXT:https://code.claude.com/docs/en/agent-view] |
| `waitingFor` | When `status` is `waiting` | `permission prompt`, `input needed` (a question from Claude or an MCP input request), `sandbox request`, `worker request` or `dialog open` [EXT:https://code.claude.com/docs/en/agent-view] |
| `sessionId`, `name` | When set | Full session UUID for `claude --resume`; an interactive session's `name` is its default display name until it is named or a plan is accepted [EXT:https://code.claude.com/docs/en/agent-view] |

| `state` | Meaning |
|---|---|
| `working` | A turn is running, or the session is between self-driven steps such as a `/loop` iteration or a CI wait; `status` says whether the process is `busy` now [EXT:https://code.claude.com/docs/en/agent-view] |
| `blocked` | The session needs the user: a question, a permission or sandbox decision, an error only the user can clear (such as an expired login), or a first prompt it was started without [EXT:https://code.claude.com/docs/en/agent-view] |
| `done` | The last turn finished and the session awaits the next prompt, process alive or not; a finished session reads `done`, never `blocked` [EXT:https://code.claude.com/docs/en/agent-view] |
| `failed`, `stopped` | The task ended with an error, or the session was stopped [EXT:https://code.claude.com/docs/en/agent-view] |

- Files under `~/.claude/jobs/<id>/` (including `state.json`) are not a stable interface, and values written to `state`, `detail`, `tempo` or `needs` are replaced on the next update; for custom progress, have the session write its own file, for example under `$CLAUDE_JOB_DIR/tmp`. [EXT:https://code.claude.com/docs/en/agent-view]
- To find a session's worktree path, the docs say to attach and check its working directory; inside a session, `/status` shows a `Session kind` row of `background job · attached`, `background job · unattended` or `interactive` (v2.1.221+). [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/commands]

## Managing background sessions

| Command | Effect |
|---|---|
| `claude attach <id\|name>` | Attach in this terminal; a name or part of one (v2.1.290+) works only while the process runs, so pass the ID to restart a stopped session [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude logs <id\|name>` | Print recent output (part of a name needs v2.1.290+) [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude stop <id>` (also `claude kill`) | Stop a session [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude respawn <id>`, `claude respawn --all` | Restart a session, running or stopped (one with a saved conversation resumes it); `--all` restarts every running session [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude rm <id>` | Remove from the list, with the worktree Claude created for it when that's safe to delete; the transcript stays available to `claude --resume` [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude rm <id> --discard-unpushed <commit>@<worktree-id>`, `claude rm <id> --force-remove-worktree <worktree-id>` | Retry after a refusal over unpushed commits (v2.1.260+) or a failed worktree removal (v2.1.268+); copy the command from the refusal message [EXT:https://code.claude.com/docs/en/agent-view] |
| `claude daemon status` | Supervisor reachability, PID, version, socket directory and live session count; exits 1 if the supervisor isn't running; warns when its version differs from the invoked `claude` [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude daemon logs`, `claude daemon run` | Follow `~/.claude/daemon.log` until `Ctrl+C`; run the supervisor in the foreground [EXT:https://code.claude.com/docs/en/cli-reference] |
| `claude daemon stop --any [--keep-workers]` | Stop the supervisor (`--any` confirms an on-demand one, the default) and its sessions, or with `--keep-workers` leave sessions for the next supervisor; the next `claude agents` or `claude --bg` starts a fresh one [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/cli-reference] |

- `claude rm` keeps a Claude-created worktree, and the session row, when it has uncommitted changes, while deleting in agent view removes it with those changes; a worktree holding commits Claude Code can't confirm are saved elsewhere makes either route refuse (`claude rm` prints `kept <id>`, agent view shows `not removed`), except that from v2.1.248 the delete succeeds when those commits are already on the local copy of `origin`'s default branch and the main checkout has that branch checked out; a worktree the user created and started the session from stays on disk; from v2.1.227 a delete keeps the session and worktree while another live Claude Code session runs inside that worktree. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/errors]
- Deleting a session stops all the background work it carried over, and when transcript cleanup has removed a stopped session's conversation, `claude respawn <id>` runs its original prompt again and `claude rm <id>` deletes the row unless Claude Code refuses. [EXT:https://code.claude.com/docs/en/agent-view]
- `/stop` stops the attached background session (or the one it is sent to as a peek reply) and keeps the transcript and any worktree, while detaching (`←`, `Ctrl+Z`, `/exit`, double `Ctrl+C` or `Ctrl+D`) never stops a session. [EXT:https://code.claude.com/docs/en/commands] [EXT:https://code.claude.com/docs/en/agent-view]

## Lifecycle

- The supervisor starts the first time a session is backgrounded or agent view opens; each session is its own Claude Code process under it, and no terminal needs to stay open. [EXT:https://code.claude.com/docs/en/agent-view]
- A process that is working (a running subagent, workflow or monitor, or a pending `/loop` wakeup, counts), paused on a dialog, or attached keeps running; one finished or waiting for the next message (a turn that ended with a question counts) and unattached for about an hour is stopped, its conversation kept on disk and resumed on attach or reply; `Ctrl+T` pins a session to keep its process. [EXT:https://code.claude.com/docs/en/agent-view]
- A process that exits unexpectedly while the supervisor runs is restarted, except a session backgrounded with `←` or `/background` and then killed, which is marked stopped; on Linux and WSL the background service checks each host process every few seconds and marks the session failed when the process exited but its connection never closed (`terminal host process died`). [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/errors]
- After an auto-update the supervisor restarts onto the new version and moves idle sessions over without interrupting working, waiting or attached ones; if the supervisor itself stops, on macOS and Linux sessions stop unless a new one connects within about a minute (`claude agents` starts one; from v2.1.295 an exiting `claude agents` doesn't start one when none is running). [EXT:https://code.claude.com/docs/en/agent-view]
- When memory stays low, the supervisor stops idle sessions, then idle pinned ones if that freed nothing; sessions survive sleep and the supervisor reconnects without treating the gap as idle (a session that was mid-response can come back unresponsive, and opening it restarts its process to continue the response). [EXT:https://code.claude.com/docs/en/agent-view]
- Shutdown stops running sessions: one waiting on input stays under `Needs input`; others show failed within 48 hours of their last progress (attach or reply restarts from the saved conversation), or, from v2.1.248, stopped with `ended while the background service was off` past 48 hours. [EXT:https://code.claude.com/docs/en/agent-view]
- When a process stops or restarts, the background shell commands and background subagents Claude started in it carry over to the next process, a dynamic workflow continues only if Claude relaunches it, and monitors and subagent-started shell commands stop; `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF=1` (v2.1.196+) stops that work instead (background subagents covered from v2.1.198), while backgrounding with `←` or `/background` still carries work over. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/env-vars]
- Permission mode, model, effort, `/model` and `/effort` changes, a `/rename` or `Ctrl+R` name, and the configuration flags the session carries persist across supervisor restarts; the flags carried when a session is backgrounded are `--mcp-config`, `--strict-mcp-config`, `--settings`, `--setting-sources`, `--add-dir`, `--plugin-dir`, `--fallback-model` and `--allow-dangerously-skip-permissions`. [EXT:https://code.claude.com/docs/en/agent-view]
- A self-paced `/loop` in a background session whose next wakeup came due while the process was down doesn't fire late and stays stopped until Claude schedules it again (reply to continue it); a notice says so from v2.1.295. [EXT:https://code.claude.com/docs/en/errors]
- State lives under the config directory (`daemon.log`, `daemon/roster.json`, `jobs/<id>/state.json`, `jobs/<id>/tmp/`), and setting `CLAUDE_CONFIG_DIR` gives a separate supervisor instance with its own sessions; `CLAUDE_JOB_DIR` is set to the session's `~/.claude/jobs/<id>` and inherited by its shell commands, `Write` and `Edit` in its `tmp` don't prompt, and the directory is removed when the session is deleted. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/env-vars]

## Permissions, isolation and git in background sessions

- A session started with `claude --bg` starts in the permission mode a new `claude` session in that directory would get ([Permission modes](goal-and-permissions.md#permission-modes)); it reads settings, including project `env` values, from the directory it runs in plus its carried flags, runs with the dispatching shell's `PATH`, and keeps that shell's cloud provider selection, `ANTHROPIC_DEFAULT_*_MODEL` aliases and `CLAUDE_CODE_EXTRA_BODY`. [EXT:https://code.claude.com/docs/en/agent-view]
- Credentials come from the supervisor (none available gives `Could not resolve authentication method`), so with `ANTHROPIC_API_KEY` the supervisor must start from a shell where it is set; gateway variables belong in a settings file's `env` block. [EXT:https://code.claude.com/docs/en/agent-view]
- `bypassPermissions` needs `skipDangerousModePermissionPrompt` in user or managed settings: with none recorded `claude --bg --permission-mode bypassPermissions` is refused, and with it only in `.claude/settings.local.json` the request is ignored and the session starts in Manual mode (or without bypass in its `Shift+Tab` cycle). [EXT:https://code.claude.com/docs/en/permission-modes]
- For `--bg` sessions the `--dangerously-skip-permissions` mode persists when the supervisor restarts the session, while `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS` has no effect because background sessions start without it. [EXT:https://code.claude.com/docs/en/cli-reference] [EXT:https://code.claude.com/docs/en/permission-modes]
- In a background session the `askUserQuestionTimeout` timer never starts, so questions wait for an answer, and permission prompts never auto-resolve on idle; in auto mode the prompt for the first read outside the working directories doesn't appear. [EXT:https://code.claude.com/docs/en/tools-reference] [EXT:https://code.claude.com/docs/en/permission-modes] With no terminal attached, commands that open a dialog can't open it and respond with a message, and for `/install-github-app` and the `/mcp` settings list the session shows under `Needs input` (v2.1.216+) until someone attaches and runs the command again; if organization settings can't load, the session prints the message and exits with status 1. [EXT:https://code.claude.com/docs/en/errors] [EXT:https://code.claude.com/docs/en/agent-view]
- A session dispatched from agent view or started with `claude --bg` starts in the working directory and, before editing, moves into its own worktree under `.claude/worktrees/`, with isolation enforced for it and its subagents (which inherit its working directory unless they use `isolation: worktree`); inside a git repository, until the move, `Edit`, `Write` and `NotebookEdit` on the shared checkout are blocked. [EXT:https://code.claude.com/docs/en/agent-view]
- The move is skipped for a session moved to the background with `←` or `/background`, one already inside a linked worktree (Claude-created or from `git worktree add`), a file inside a linked worktree, a non-git directory with no `WorktreeCreate` hook (such sessions aren't isolated from each other), and writes outside the working directory. [EXT:https://code.claude.com/docs/en/agent-view]
- After code changes in a worktree Claude entered, Claude Code instructs Claude to commit without asking, push the branch when there is a remote, and open a draft PR when the task calls for it (v2.1.198+), never pushing to `main` or `master`, force-pushing or merging, with git instructions in the task, `CLAUDE.md` or memory taking precedence; a session editing a checkout it didn't isolate itself (`bgIsolation` `"none"`, a failed move, or a pre-existing worktree) still asks before committing or switching branches, and every job ends with a report of what it did and where the work is. [EXT:https://code.claude.com/docs/en/agent-view]

## Limits and notifications

- Background sessions consume subscription usage like interactive ones (ten in parallel use quota roughly ten times as fast). [EXT:https://code.claude.com/docs/en/agent-view] Usage counts against the session and weekly allowances at the same time, so a single burst of heavy activity, such as a large workflow fanout, can exhaust the weekly allowance before the session window resets. [EXT:https://code.claude.com/docs/en/errors] See [Limits](limits-and-caching.md).
- The usage-limit wait is not offered in background sessions or `-p` runs, and moving a session to the background ends a pending wait without continuing; a dynamic workflow in a background session doesn't pause at a claude.ai usage limit, so the affected agent fails. [EXT:https://code.claude.com/docs/en/interactive-mode] [EXT:https://code.claude.com/docs/en/workflows]
- When a Fable usage-credits consent prompt in a background session closes with nobody answering, the turn ends with nothing sent; attach, send another prompt and answer the consent prompt when it reappears. [EXT:https://code.claude.com/docs/en/errors] Each row-summary refresh (end of turn and each mid-turn rewrite) is one short billed request through the normal provider, generated by a Haiku-class model. [EXT:https://code.claude.com/docs/en/agent-view]
- Notifications for a session needing input, finishing or failing are sent only while agent view is open and fire the `Notification` hook with `agent_needs_input` or `agent_completed` (v2.1.198+); scheduled sessions such as `/loop` notify only when they need input. [EXT:https://code.claude.com/docs/en/agent-view] [EXT:https://code.claude.com/docs/en/hooks]
