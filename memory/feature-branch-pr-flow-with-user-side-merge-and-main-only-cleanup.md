# Feature-branch PR flow with user-side merge and main-only cleanup

Every change goes through a fresh branch off main, a commit, a push and a PR against main; the user merges the PR themselves, and after the merge the branch is cleaned up locally and remotely so only main persists. The user stated it in the same form across sessions: "create a new branch off main, commit, push, open a PR against main. Once merged, clean the branch" (2026-06-08), "create a new branch off main" (2026-06-04, twice), "create new branch off main, commit and open a PR" (2026-08-06), "merged. clean up the local and remote branch you just created" (2026-06-03) and the sweep "delete all local and remote branches except main" (2026-08-07). So: branch off main, open the PR, then stop and wait for the user's "merged"; never merge it or push to main directly (the protected-branch guard registered in `.claude/settings.local.json` refuses commits and pushes from main anyway); after the merge, delete the branch locally and remotely (from main that is `gh api -X DELETE repos/armelhbobdad/bmad-module-ultracode-goal/git/refs/heads/<branch>` plus `git fetch --prune`). CONTRIBUTING.md documents the contributor PR flow but not that the maintainer merges and expects the branch cleaned afterwards.

On 2026-10-24 (session 3db662c1-d326-4c49-93fb-f5b18179d765) the user widened the merge part: "You also have the authorisation to merge PR when necessary and you can call if when you really need my critical decision". So the assistant may now merge a PR itself when the work needs it, for example landing a stacked series in order once CI is green, with a merge commit (`gh pr merge <n> --merge`) as the user's merges are, then clean up as above. It still never pushes to main directly, and it still stops for a decision that is genuinely the user's.

A plain `gh pr merge <n> --merge` is refused here: `gh pr view <n> --json mergeStateStatus,reviewDecision` reads `BLOCKED` / `REVIEW_REQUIRED`, because the active `main-protection` ruleset (`gh api repos/armelhbobdad/bmad-module-ultracode-goal/rulesets`; classic branch protection returns 404 "Branch not protected") requires an approving review, and the owner who opens the PRs cannot approve their own. The owner merges by admin bypass: PR #223 was merged by armelhbobdad with `reviewDecision` REVIEW_REQUIRED and no reviews. So on the user's "merge", run `gh pr merge <n> --merge --admin --delete-branch` from the PR branch (2026-11-14, PR #228). The bypass covers every rule of the ruleset, not only the review: its one bypass actor is the Admin repository role (`bypass_mode: pull_request`), and it also lists ten required status checks (prettier, eslint, markdownlint, lintlang, em-dash, docs-links, and validate and python on ubuntu-latest and windows-latest). So `--admin` merges even while those checks are still running or red. #228 was merged only after `gh pr checks 228` showed all ten passing. The same review rule makes a "merged" from the user no proof: on 2026-11-14 the user replied "merged" for PR #231 while `gh pr view 231 --json state,mergedAt` still read OPEN, so the assistant merged it itself with `gh pr merge 231 --merge --admin --delete-branch` once all 10 required checks were green. Read `gh pr view <n> --json state,mergedAt` before any branch cleanup, because deleting the remote head branch of a still-open PR closes it unmerged.

The repo's `deleteBranchOnMerge: false` leaves the head branch behind, and `--delete-branch` does not reliably clean it up. Run from the PR branch on #228 it deleted the remote and local branch and switched to an updated main, but on Skill Forge PR #1234 (2026-11-16) it switched the clone to main and deleted the local branch while `git ls-remote --heads origin test/health-check-shared-fixture` still listed the branch afterwards (the cause was not established). With -R/--repo it deletes only the remote branch and never switches or deletes locally: after `gh pr merge 245 --repo armelhbobdad/bmad-module-ultracode-goal --merge --admin --delete-branch` (2026-11-18), `git branch --show-current` still printed `fix/health-check-repo-host` while `git ls-remote --heads origin fix/health-check-repo-host` counted 0, and the checkout stays on the merged branch until `git switch main`, `git pull` and `git branch -d`. So after any such merge, check `git ls-remote --heads origin <branch>`, delete a survivor with `gh api -X DELETE repos/armelhbobdad/<repo>/git/refs/heads/<branch>`, and switch to main and delete the local branch when gh did not.
