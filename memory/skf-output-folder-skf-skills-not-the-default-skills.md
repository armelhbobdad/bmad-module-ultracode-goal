# SKF output folder skf-skills, not the default skills

This module's source lives under `skills/` (293 of 384 tracked files at v2.2.0), which is also the SKF installer's default `skills_output_folder`, so with the default, generated skills land in the source tree. On 2026-09-23 the user settled it: "Change `skills_output_folder` to `skf-skills`. It should be committed." The value lives in `_bmad/skf/config.yaml` and in the install answers at `_bmad/_config/skf-manifest.yaml`, both gitignored and so per-checkout: a fresh install asks "Where should generated skills be saved?" again, defaulting to `skills`, and has to be answered `skf-skills`. The user also confirmed keeping `skf-skills` excluded from the ccc index and listing `/skf-skills/` in `.npmignore`: `package.json` has no `files` list, so a committed folder would otherwise ship in every published package, the clean CI release included. The npm release of SKF (2.2.0, published 2026-09-22) ships a `skf-merge-ccc-exclusions.py` that reports `version: v1`, writes `**/skf-skills` and only ever adds patterns, so a stale `**/skills` left by an earlier run has to be deleted from `.cocoindex_code/settings.yml` by hand. Upstream #491 and #492 were closed on 2026-09-26 by PR #493 on SKF main, which is unreleased (a local checkout at `v2.2.0-46` still reads VERSION 2.2.0): installed from that checkout, the helper (`version: v2`) replaced `**/skf-skills` and `**/forge-data` with root-anchored `skf-skills` and `forge-data` in a 2026-09-28 skf-setup run and pruned the patterns it had recorded in `forge-tier.yaml`, and per its docstring it leaves a configured folder that holds only non-SKF content out of the exclusions, with a warning.
