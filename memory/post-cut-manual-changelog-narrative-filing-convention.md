# Post-cut manual CHANGELOG narrative filing convention

A release's CHANGELOG narrative is filed by hand after the release lands: `[Unreleased]` is left empty before `gh workflow run release.yaml -f version_bump=<bump>`, the fact-checked narrative is staged in the gitignored `_bmad-output/ultracode-goal/release-notes-<version>-narrative.md`, and once the bot PR merges it is woven under the new version heading in a docs PR; in the user's words, "file the narrative and re-cut comparison.md". The reason is that release.yaml's `conventional-changelog-cli` step prepends a generated section and never drains `[Unreleased]`, and the following "Restore CHANGELOG preamble" awk (`^## \[[0-9]`) treats the whole `[Unreleased]` block as preamble, so any narrative sitting there at dispatch is stranded above the new heading, which is how 2.0.0 (#85) and 2.1.0 (#98) mis-filed and were moved by hand. The stage-in-`_bmad-output` practice began at 2.2.0 (#104, 2cd09c6) and supersedes writing the narrative under `[Unreleased]` beforehand. A drain automation was built, adversarially reviewed and deliberately parked, so hand filing is the working practice rather than a settled design; nothing tracked enforces the empty `[Unreleased]`, and [RELEASING.md](../docs/_internal/RELEASING.md) does not mention the manual filing. When weaving, a hand-filed `###` must not repeat the name of a generated sibling under the same `## [X.Y.Z]`: the conventionalcommits preset emits `### Features`, `### Bug Fixes`, `### Performance Improvements`, `### Reverts` and `### ⚠ BREAKING CHANGES`, `.markdownlint-cli2.yaml` sets `MD024: siblings_only: true`, and a repeated name fails with `error MD024/no-duplicate-heading Multiple headings with the same content [Context: "Added"]` (hit on 2026-08-02 in session 33431228 with two `### Added` under one version, caught first by the lint-staged pre-commit hook), so use the Keep-a-Changelog set (Added, Changed, Deprecated, Removed, Fixed, Security) as 2.1.0 and 2.2.0 do.
