# deep_merge move to config_utils.structural_merge in BMAD 6.11

BMAD Method 6.11.0 (stable, published 2026-08-10) moved the customization structural merge out of `_bmad/scripts/resolve_customization.py`, where the earlier releases that ship that resolver define it as `deep_merge`, into `_bmad/scripts/config_utils.py` as `structural_merge`, which the resolver applies through `load_customization` and `merge_layers`. The move first shipped in the 6.10.1-next.24 prerelease (2026-07-28), while 6.10.1-next.0 to next.23 still define `deep_merge`, and 6.11.0's `config_utils.py` is byte-identical to 6.12.4's. UCG's `skills/ultracode-goal/scripts/merge_customization.py` imported only `deep_merge`, so on those releases every installer Step 6b awareness fragment failed with "merge engine (resolve_customization.py) missing" (exit 2) and none of the `_bmad/custom/{bmad-prd,bmad-architecture,bmad-create-epics-and-stories,ucg-create-story}.toml` overlays was written; the first release with an engine change is found from the published tarballs (`npm pack bmad-method@<version>`, then `tar -xOzf` on `package/src/scripts/resolve_customization.py`), not from the release one project has installed. Since PR #145 (commit eaa60a9) `_resolve_merge_engine` in that script imports `deep_merge` where it exists and otherwise `config_utils.structural_merge`, still requiring `resolve_customization.py`; `structural_merge([], facts)` on a string list appends exactly as `deep_merge` does. Every tool-running test in `test_merge_customization.py`, `test_no_harm.py` and `test_tea_fragments.py` runs once per engine in their hard-coded `ENGINES` maps (`fixtures/engine/` before 6.11, `fixtures/engine-6.12/`), and `test/test-cli-integration.js` adds one 6.12 Step 6b case and its twin; a later move of the merge function needs a new import branch in `_resolve_merge_engine`, a new fixture folder, an `ENGINES` entry in all three suites, a Step 6b case and a `VENDORED_DIRS` entry in `tools/validate-no-em-dash.js`.
