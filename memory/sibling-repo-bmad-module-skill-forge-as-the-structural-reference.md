# Sibling repo bmad-module-skill-forge as the structural reference

This repository is standardized on the sister module bmad-module-skill-forge (a sibling checkout, `../bmad-module-skill-forge` from this repo): the user asked to "standardize our module repo following what we did for the skf module [the sibling checkout] . I mean, the best ever readme, docs, CI gates, installer, etc...." and later to "add the astro light website inspired by [the sibling checkout]/website/". README.md, docs/, the five workflows under .github/workflows/, tools/cli/lib/installer.js and website/astro.config.mjs are modelled on skill-forge, and structural questions are answered by looking there first. Tools that exist in both repos (validate-docs-links.js, validate-file-refs.js, validate-skills.js) keep their code bodies converged and differ only in header comments or module-specific constants; the CI workflows, installer and Astro config follow skill-forge in file set and job shape but are not byte-converged and are not expected to be (skill-forge is ahead on action versions; this repo adds a validate:fixtures gate and uv/python setup). One deliberate divergence, not a convergence target: links between docs/ pages are written page-relative here (`[gate model](./gate-model.md)`, chosen in commit 66dd14d; 56 `./` targets and no `/docs/` targets at v2.2.0), while skill-forge writes them root-absolute (`/docs/page.md`) because its `tools/fix-doc-links.js` rewrites every link to that form. This repository has no fixer, so a page ported from the sibling arrives root-absolute and is re-linked by hand; both forms build and pass `node tools/validate-docs-links.js --strict`, so a mixed tree is never flagged (the form is the assistant's record of session 3b719ab6, not user words).
