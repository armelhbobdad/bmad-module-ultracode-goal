# Repo guard refusing commits in other repositories from a UCG session

This repository's PreToolUse guard (`skills/ultracode-goal/scripts/hooks/guard_pretooluse.py`, armed from the gitignored `.claude/settings.local.json` with `ULTRACODE_PROTECTED_BRANCHES=main,master`) reads the branch, and the staged index, from the hook event's `cwd`, the session's working directory, not from the repository a command targets. Its docstring (`:9-14`) calls this deliberate. So while this checkout sits on `main`, a commit in another checkout on a feature branch is refused with "PreToolUse:Bash hook error: Protected-branch guard: refusing `git commit` on 'main'", both as `cd ../bmad-module-skill-forge && git commit ...` and as `git -C ../bmad-module-skill-forge commit ...`. `git push` is refused the same way. Hit on 2026-11-15 while committing Skill Forge's side of #226 from a session started here.

Putting this checkout on a feature branch does not get through either, because the empty-index gate reads this checkout's index: on 2026-11-16, with UCG on a feature branch and nothing staged here, `cd ../bmad-module-skill-forge && git commit -F <msg>` was refused with "PreToolUse:Bash hook error: Empty-index guard: refusing `git commit`" and "the staged index is empty (or could not be read)", although Skill Forge had its changes staged. On 2026-11-03 review subagents building fixture repos under the scratchpad had every `git commit` there refused with "Empty-index guard: refusing `git commit`"; they built fixture history with `git write-tree` / `git commit-tree` / `git update-ref` instead, and one agent found commit-tree refused as well and fell back to fixtures with an unborn HEAD and staged entries only, so tell a workflow agent that needs commits in a scratch repo up front. The way through: the user runs that commit or push with the `!` prefix (`! git -C <skill-forge checkout> commit -F <msg>` landed as 648fd488), or the other repository's work runs in a session started in that repository, where this hook is not loaded. Do not switch this checkout off `main` to pass the guard. Related: [[repo-guard-reading-a-commit-revision-suffix-as-a-git-commit]], [[remote-branch-deletion-via-gh-api-while-on-main]].

The same holds for this repository's own linked worktrees and for workflow subagents, which start in the session's `cwd`. On 2026-11-23 four build agents working in `git worktree add` checkouts on feature branches each had `git add` pass and the separate `git commit` refused with "Protected-branch guard: refusing `git commit` on 'main'", and so was a probe agent's first commit in a throwaway repository under `/tmp`. A hand-made hook event fed to the guard with the worktree as `cwd` passes, so that dry run does not show what a session will meet. What worked for this repository's worktrees: move them under `.claude/worktrees/` (`git worktree move`), switch the main session into each with the EnterWorktree tool (`path`), which makes the hook's `cwd` that worktree, commit and push there, then leave with ExitWorktree `keep`. Inside, Claude Code refuses compound shell commands and any git command aimed outside the worktree ("too complex to verify that it stays inside the worktree"), so run one plain command per call and write message files with the Write tool. Agents that only edit and stage, with the main session committing, avoid the refusal altogether; the throwaway repository's first commit was made by the user with the `!` prefix.
