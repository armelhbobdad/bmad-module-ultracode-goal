# Security Policy

## Supported Versions

UCG is pre-1.0. Security fixes land on the latest `0.x` release only. There is no long-term support branch yet; upgrade to the newest published version before reporting a vulnerability.

| Version | Supported          |
| ------- | ------------------ |
| latest `0.x` | yes           |
| older `0.x`  | no, upgrade first |

## Reporting a Vulnerability

**Do not open a public issue for a security problem.** Report it privately through GitHub's [private vulnerability reporting](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately) on this repository: open a draft Security Advisory from the **Security** tab.

UCG is maintained in spare hours. Expect an acknowledgement within a few days, not within hours. We'll confirm the report, agree on a disclosure timeline, and credit you in the advisory unless you ask otherwise.

## Hook Security

UCG installs Claude Code hooks at preflight so that a set of invariants is enforced by the runtime rather than left to the model's memory (which is context, not enforcement). This section is the full account of what that means.

**What UCG installs:**

- A **`PreToolUse` guard** that validates story markers and git state before a tool runs and, while a run latch is present, keeps the model's tool calls away from claude-mem and from the Cross-Session Recall store, and stops them from changing the latch itself. It enforces seven invariants:
  1. denies a `git commit`/`git push` on a protected branch. "Protected branch" means the branch of the directory **Claude Code is running in**, not the repository the command targets, so a `cd /elsewhere && git commit` is denied whenever the session's own repo sits on `main`, even when the other repo is on a feature branch;
  2. denies a `git commit` until a "tests-ran" marker exists for the current story;
  3. denies a `git commit` unless that marker's `baseline=<sha>` matches the SHA the story recorded at start (so a marker replayed from an earlier code state is rejected);
  4. denies a `git commit` while the staged index is empty, or while the staged-index probe cannot answer;
  5. when the guard is armed with `ULTRACODE_TEST_ARTIFACTS`, denies a `git commit` while the staged content of any acceptance-test file the story's atdd-checklist lists in its `generatedTestFiles` frontmatter (or, for a checklist with no such list, names anywhere in its text) still contains `test.skip(`, or while that list cannot be read;
  6. while a UCG run latch (`.mem-state.json` in the implementation artifacts folder) is present, denies every claude-mem MCP call, in the plugin form (`mcp__plugin_claude-mem_<server>__<op>`) and both bare-server forms (`mcp__claude-mem__<op>` and `mcp__claude_mem__<op>`), every MCP resource read or listing on a claude-mem server, every MCP resource listing that names no server (it lists every server's resources, claude-mem's included), and any Read, Grep, Glob, Write, Edit, MultiEdit, NotebookEdit, or Bash call that names `.claude-mem` (the name anywhere in the call, quoted or escaped, or a path, symlink, glob, or brace expansion that reaches that folder under your home, but not a search of a folder above it: see the limits below), whatever the latch's format or color. There is no green path: UCG no longer uses claude-mem, so no latch lets a claude-mem call through. Outside a run, your own claude-mem usage is never touched, with one caveat. The guard counts a present latch as a live run, and the hooks stay armed after a run ends. A run removes its own latch at each of its exits (Finalize, a preflight stop, the headless exit path, or any other stop before Finalize) with `mem_recall.py unlatch`. A latch left behind by a run that died before any of those exits keeps denying, in your later sessions too, until the next run's Stage 1 replaces it or you delete it by hand. Each deny a latch causes names the latch file and ends with a note for you: if no run is active, delete that file by hand. The same note tells the model not to remove the latch itself;
  7. while a run latch is present, stops the model's tool calls from changing the latch file and, when the latch names a recall store, from reaching that store:
     - **The latch file**, whatever the latch holds. A Write, Edit, MultiEdit, or NotebookEdit call that names it is denied. So is a Bash segment that names it, by its path or by its file name `.mem-state.json` on its own, trailing dots included since Windows drops them (so a `cd` into its folder first changes nothing), unless the guard can tell the segment only reads it: `rm`, `mv`, `cp`, `ln`, `tee`, a redirection, `sed -i`, `truncate`, and `python -c` are all denied, and so is anything else that is not such a read. Read, Grep, and Glob calls are left alone, since the run reads the latch at Finalize.
     - **The recall store**, when the latch names one. It names one whenever `cross_session_recall_store` is set to a usable folder, with recall on or off. A Read, Grep, Glob, Write, Edit, MultiEdit, NotebookEdit, or Bash call that names the store or a path inside it is denied.

     A Bash segment that names the latch counts as a read only when all of these hold:
     - its command is `[`, `[[`, `cat`, `egrep`, `fgrep`, `grep`, `head`, `jq`, `ls`, `stat`, `tail`, `test`, or `wc`, by that bare name (`./cat` is not one);
     - it holds no `>`, backtick, `$(`, `<(`, or `=~` anywhere, even inside quotes, so no output redirection (`>`, `>>`, `2>`, `&>`, `<>`), no command or process substitution, and no `[[ ... =~ ... ]]` match, which hands what it matched on through `BASH_REMATCH`;
     - it has none of the leading assignments listed for the recall scripts below (such as `PATH=` or `LD_PRELOAD=`);
     - nothing in the command changes the environment or command lookup (as for the recall scripts below), and the command holds no `$_`;
     - if the command holds a pipe (`|`), every segment of it is such a read.

     The guard reads a path the same way for both:
     - it reads `file_path` and `path`, NotebookEdit's `notebook_path`, Glob's `pattern`, Grep's `glob`, and each segment of a Bash command, on the tools each one covers;
     - it reads a Bash command without each heredoc body it can tell bash only hands to `cat` or `tee` as data (the conditions follow this list), and reads every other body as commands;
     - it resolves `~`, `~+`, `$HOME`, `${HOME}` and forms such as `${HOME:-...}`, `%USERPROFILE%`, `$PWD`, `$(pwd)` and a backtick `pwd`, `$'...'` escapes, absolute paths, paths relative to the session's working directory, and symlinks;
     - it finds the path inside a longer word (such as `-o<store>` or `file://<store>`), and a glob, an extglob group (such as `@(...)` or `!(...)`), or a brace expansion that can match it;
     - it folds letter case and separators on Windows, and letter case and Unicode form on macOS.

     A heredoc body is left out only when all of these hold. Then all of it is left out when its delimiter is quoted (`<<'EOF'`, `<<"EOF"`, `<<\EOF`), and when it is not, all but each `$(...)`, `$((...))`, `${...}`, `$[...]`, and backtick, which bash runs and the guard still reads:
     - its simple command is led by `cat` or `tee`, by that bare name, after plain variable assignments only (no quote or expansion in the value, and none of the leading assignments listed for the recall scripts below, such as `PATH=`), with nothing else in front: no keyword (such as `then` or `time`), no `{` or `!`, and no redirection. So the body of `bash`, `python3 -`, `xargs`, `source /dev/stdin`, or `then cat` is read;
     - no pipe (`|` or `|&`) follows that command in its pipeline, before the next `;`, `&`, `&&`, `||`, or the end of its line, so `cat <<'EOF' |` with `sh` on the line after the body has its body read. A pipe anywhere else in the command does not count;
     - nothing before that command changes the environment or command lookup, as for the recall scripts below. Here that also rules out `((...))`, `$((...))`, a `for` loop, a `${...}` that assigns, and any `NAME=` or `NAME[...]=`, even in an argument such as `CC=gcc` (but not one led by `-`, `.`, or `/`, such as `--format=`). Such a change after it does not count;
     - when a `(` (other than the one in `$(`, `$((`, or `((`) or a word `{`, `if`, `while`, `until`, `for`, `select`, `function`, or `coproc`, outside quotes and comments, comes anywhere before that command, the command holds no `|` at all, even inside quotes, and nothing anywhere in it changes the environment or command lookup in the sense of the item above, since a group, a subshell, a loop, or a function can pipe the body into a shell or run it again;
     - the command holds no `<(` or `>(` outside its heredoc bodies, even inside quotes;
     - the guard can read every heredoc in the command the way bash does. It cannot, for example, when one sits inside `$(...)`, backticks, or `[[ ]]`, when the command holds a `case` or a `$[`, or arithmetic that spans lines or holds a quote, when a delimiter is not a name (bare, quoted whole, or after a backslash), when no delimiter line ends a body, when a line of an unquoted body ends in a backslash, or when a second, quote-aware reading of the command finds other delimiters (an apostrophe in a comment on an operator's line is enough).

     Only the recall scripts get through. A Bash segment that names the store, or names the latch and is not a read, is let through only when all of these hold:
     - it runs this skill's own `scripts/mem_recall.py` or `scripts/mem_observation.py`, by the path the skill is installed at, directly after `uv run`, `python`, `python3`, or `python3.N`;
     - it is a shell segment of its own;
     - it has no redirection (`>`, `>>`, `<`, `2>`, `&>`) and no command substitution (`$(...)` or backticks);
     - it has no wrapper such as `env`, `sudo`, or `bash -c`;
     - it has no leading assignment that changes which interpreter, libraries, configuration, or home folder the call uses (such as `PATH=`, `PYTHONPATH=`, `UV_PYTHON=`, `HOME=`, or `GIT_CONFIG_COUNT=`);
     - nothing else in the same command changes the environment or what `uv` and `python` resolve to (an assignment of its own, `export`, `source`, a function definition, `hash`, `alias`, `eval`, and the like). This counts what can make such a change without a plain `NAME=` too: any `((...))`, `$((...))`, or `$[...]`; any mention of `BASH_CMDS` or `BASH_ALIASES`, even one that only reads them (such as `${#BASH_CMDS[@]}` or `grep BASH_CMDS`), since a command whose name the text does not spell can write an entry; a `${...}` whose operator assigns, a `=` or `:=` right after the name and any subscript (`${x:=...}`, `${BASH_CMDS[cat]=...}`, `${!x:=...}`); an assignment, a compound assignment such as `+=`, a `++`, or a `--` where bash evaluates arithmetic: glued to a name or a `]` in a `[[ ... ]]` test that compares numbers (`-eq`, `-ne`, `-lt`, `-le`, `-gt`, or `-ge`, as in `[[ 1 -eq PATH=1 ]]`), and, blanks allowed, in a `${...}` substring's offset or length (`${PWD:PATH=1}`) or in a subscript inside a `${...}`, in a word that assigns to it, or in a `test`, `[`, or `[[ ... ]]` that holds a `-v` or `-R` or compares numbers (`${a[PATH=1]}`, `a[i++]=x`, `test -v 'a[PATH=1]'`); an assignment to one of the interpreter or path variables above whose value opens a `$(...)` or backtick (`PATH=$(...)`); a rebinding builtin behind `command`, and an assignment behind the `time` keyword, which run in the shell as they do at the head (`command export PATH=...`, `time PATH=...`), though `command -v` and `-V` only look a name up; and an assignment word whose subscript nests or holds blanks (`PATH[a[0]]=...`, `PATH[ 0 ]=...`). A `=` later in a `${...}` than its operator (`${PWD#*=}`, `${x:-a=b}`) and a bracket bash does not evaluate as a subscript (the character class in `grep 'a[b=c]'`) do not count. The guard reads the command's text, so it cannot see a change that only happens when the command runs: a command name built at run time (`$(echo export) PATH=...`), or a value that only reaches arithmetic at run time (`set -- PATH=1; [[ $1 -eq 1 ]]`, `[[ $(printf %s PATH=1) -eq 1 ]]`), each before a read of the latch, still counts as a read.

     So only `mem_recall.py` changes the latch: `latch` writes it at Stage 1, and `unlatch` removes it at each exit, only when it carries that run's id. Each deny invariant 7 causes names the latch file and ends with the same note as invariant 6.

  Invariants 1 to 5 treat every git subcommand that is not one of git's built-in commands as both a commit and a push, so all five checks apply to it. What an alias runs lives in git's configuration, and whether `git <name>` runs an external `git-<name>` command instead depends on PATH; the command can change either before git starts (its own options, an earlier segment, a wrapper, a nested shell, the environment), and the hook's PATH can differ from the shell's, so the guard reads neither. It clears only a built-in command, which git runs before any alias and nothing can move, spelled as git spells it (git matches its command names case-sensitively, so `git LOG` runs `alias.log`), and one of the commands git ships as scripts in its exec-path (`submodule`, `mergetool`, `filter-branch`, `request-pull`, `quiltimport`) while the command does not mention that path. So `git ci` with `alias.ci = commit` counts as a commit and a push, and so do a read-only alias such as `git st`, an external command such as `git lfs`, a built-in newer than the guard's list (`git hook`), and a typo. The deny names the subcommand and says to run the git command an alias stands for, or an external command by its own name (`git-lfs pull`). The guard also classifies the commands inside `$(...)`, `<(...)` and backticks outside single quotes, the arguments of `eval` (behind a wrapper too) and a command run by `exec`, and reads each command once more as bash reads it (quotes, newlines, a function definition's body), so a quoted `;`, `&&` or `|` in an argument (`git ci -m 'fix: a; b'`) no longer hides the subcommand. Residual, stated rather than hidden: the guard reads a command's text, not what runs. A git command that runs other commands (`rebase --exec`, `bisect run`, `submodule foreach`, `difftool --extcmd`) counts as itself, and so does anything the text does not show, such as a script's contents or a function defined in an earlier call. And the guard can only classify what it can lex: in a command none of its readings can tokenize (an unbalanced quote, or an apostrophe in a comment or heredoc its rough comment and heredoc reading misses, around a construct only a full shell parser reads), an alias can still pass, while a literal `git commit` or `git push` is still found by the matches-anywhere scan. The tests-ran marker and the remote's branch protection stand behind them.

  Read the failure behavior before you rely on any of these. Invariants 2, 3, 4, 6, and 7 fail **closed**: an unreadable marker or story pointer (`.current-story`) or an unanswerable staged-index probe denies the commit, a latch that is present but cannot be read still denies every claude-mem call and every change to the latch file, and an error while checking any call against a present latch denies that call, rather than waving it through. The reading of a Bash command that invariants 1 to 5 share fails closed too: a command the guard cannot classify, because reading it raised an error, is denied on any branch, and a segment that puts more than 32 exec wrappers (`env`, `nice`, `sudo`, and the others) ahead of its command counts as both a commit and a push, whatever that command is. So do their checks: an error raised while checking a commit or push (a NUL byte in a test-file path the checklist lists, say) denies it. Any other error the guard raises while deciding on a call (an event or a Bash input that is not a JSON object, or JSON nested deeper than Python reads) denies that call too, and the deny names the error, so the guard exits with a decision, allow or deny, on every call it runs for. A crash it cannot catch itself (an interpreter that cannot start, an error before its code runs, a timeout) makes no decision, so the command would go through. Invariant 7's store half compares against the store path the latch records, so a latch with no usable one (the store key unset or not set to a usable folder, a latch in the older format, or a latch that cannot be read) puts that half out of scope: such a latch denies nothing by store path, while invariant 6 and the latch-file half of invariant 7 still apply. The other two make no decision when their input is unavailable. Invariant 1 fails **open**: if `git rev-parse` cannot report a branch (git missing, or the 10s timeout), there is no branch to match against the protected list and the command proceeds. Invariant 5 is simply out of scope when `ULTRACODE_TEST_ARTIFACTS` is unset, emitting an advisory note and never a deny, so that hooks armed by a run predating the un-skip proof do not brick commits over a checklist that run never wrote; within scope it fails closed.

  Invariants 6 and 7 have limits, accepted and stated here rather than hidden. Invariant 7 matches the store and the latch as a tool call spells them, so it does not follow indirection: a `cd` and then a relative path to the store (for the latch, its file name on its own counts, so that form is denied), a variable holding part of the path or of the file name, a glob such as `.*` that matches every hidden file, or a script or other file whose contents name them (the guard reads the paths a call names, not what a Write, or a heredoc fed to `cat` or `tee`, puts into a file). It also lets through a search of a folder above the store, a repo-wide search that reaches a store inside your workspace, a command on a folder above the latch (such as removing the implementation artifacts folder, `git clean -fdx`, or `git stash --all`), a Git Bash drive path (`/c/...`), a Windows 8.3 short name or admin-share path, and any tool other than the ones it names. Invariant 6 likewise lets through a search of a folder above `.claude-mem`, such as a Grep or a `grep -r` of your home folder, or a `**` glob from it, and it does not see a Bash call to claude-mem's local HTTP service. The exemption checks the script's path, not its arguments, so the model could still run the pinned calls itself: `mem_recall.py unlatch` with the run id it reads from the latch, or `mem_recall.py latch` again with no store, which puts the store half out of scope. Only the run's own steps and the note at the end of each deny tell it not to. The exemption also trusts what the pinned call loads. It pins each recall script's path, not its content, so an edited recall script, `lib/mem_common.py`, or anything else that call loads still gets through, for example when the model edits it in a skill installed inside your workspace. It also trusts the interpreter `uv` or `python` resolves to and the configuration they read, so a `.python-version` or `uv.toml` file written into the working folder can name another interpreter for the pinned call.

  Other forms fail closed instead, so the call is denied and the store stays shut. A genuine recall call is denied when its script path is written with `~`, a variable, a Git Bash drive path (`/c/...`), or (on Windows) unquoted backslashes; when it gives a relative script path in a command where `cd`, `pushd`, or `popd` appears; when an option comes before the script (`uv run --with ...`, `python -I ...`); when its segment holds a `<`, `>`, backtick, or `$(` anywhere, even inside quotes, so `2>&1`, `2>/dev/null`, and `$((...))` too; when a `;`, `|`, `&`, or newline sits inside a quoted argument, or the call is split by a line continuation, since the guard splits a command at those characters whatever the quoting; and when anything else in the same command changes the environment. The guard matches text, not intent, so a command that only mentions the store path or `.claude-mem`, in a commit message, a search pattern, or a heredoc body it reads as commands, is denied as well, and so is a command that only mentions the latch's path or its file name, unless it counts as a read. A mention of `.claude-mem` is denied in any heredoc body, data or not. A command that only reads the latch is denied too when the guard cannot tell it only reads it: a read command given by a path (`/bin/cat`), a read with any output redirection (so `2>/dev/null` too), a read piped into another kind of command, a read whose quoted argument holds a `|` (such as `grep -E 'a|b'`, since the guard splits at `|` whatever the quoting), or a command that holds `$_`. A store set to your workspace, to a folder above it (such as `~`), or to a folder that holds the implementation artifacts makes nearly every call there name the store, since a bare word in a Bash command resolves against the working folder: every Bash command run inside it is denied except the recall scripts' own calls, and a store that holds the implementation artifacts also denies the run's own marker writes. Give the store a folder of its own, such as `~/.ultracode-goal/recall`.

  One limit covers all seven invariants, and no invariant can close it: a Claude Code [mod](https://code.claude.com/docs/en/plugins/mods/overview). A mod is a plugin whose code runs inside Claude Code. A mod you install that handles the `tool.check` event answers after the `PreToolUse` hooks have run. In a session with neither managed settings nor a Team or Enterprise `/login` as its credential, that mod can approve a call the guard denied, or one that a deny rule refuses. A session that runs on an API key or a long-lived `CLAUDE_CODE_OAUTH_TOKEN` is not using that login, even when one is stored. A mod's hooks run under `claude -p` too, so a headless run is no exception. Before a UCG run, review every mod you have installed. In a terminal session, `/plugin` lists the mods that session loaded. With managed settings on the machine, or a Team or Enterprise `/login` as the session's credential, a mod's approval does not get a call past the guard, by default.
- A **`Stop` hook** that tracks the per-story turn budget and surfaces an escalation when the run overruns `max_turns_per_story`. This hook records the overrun and lets the stop proceed; it never blocks.

**Where they live:** in your **machine-local, gitignored `.claude/settings.local.json`**, auto-merged at preflight. They are never written to a committed file and never travel with the repo. The same write adds `permissions.allow` rules for the commands in `allowlist_commands` (the test, lint and build commands, `git add` and `git commit`, and the like), so an unattended run is not stopped by a permission prompt nobody can answer. Each entry becomes a `Bash(<entry>:*)` rule, which also allows anything after the entry. So the default `uv run` entry, which the run's own scripts need, lets any program run through `uv run` without a prompt: the allow rules spare prompts, and the invariants above are what the guard enforces. Claude Code treats this file as protected: under Auto Mode its permission classifier reviews the write and may refuse it, or the calls after it. An attended run then stops and asks you to approve or apply the change yourself; a headless run stops with a blocker naming the write (see [Getting Started](https://armelhbobdad.github.io/bmad-module-ultracode-goal/getting-started/#hook-security)).

**What they execute:** the hooks run, via `uv run`, two zero-dependency PEP 723 Python scripts shipped inside the skill:

- `skills/ultracode-goal/scripts/hooks/guard_pretooluse.py`
- `skills/ultracode-goal/scripts/hooks/budget_stop.py`

Both declare `dependencies = []`. They read a JSON event on stdin, inspect git/local state, and emit a JSON decision: no network calls, no third-party packages.

**How to inspect them:** read the two scripts. They are plain Python with a documented hook contract in their module docstrings. The guard's docstring enumerates the seven invariants above; confirm for yourself that it only ever denies a tool call and never mutates your repo, and that the only thing the budget hook does is count turns.

**How to remove them:** delete the corresponding `PreToolUse` and `Stop` hook entries, and the `permissions.allow` entries preflight added, from `.claude/settings.local.json`. Because the file is machine-local and gitignored, nothing else in your repo depends on them.

## Secrets

The UCG module never requires you to provide secrets. It does not read, store, or transmit credentials as part of its own operation. In a **headless** run, a secret the run cannot resolve is treated as a **red blocker** that halts the run, never as an interactive prompt and never as a value the conductor invents to keep moving.

## Optional third-party integrations

One knob lets a run reach a third-party tool. It ships **off**, it is advisory (it cannot affect a gate verdict), and with it off the run behaves as though the tool did not exist. What it does when you turn it on:

- **[Knowledge-graph refresh](https://armelhbobdad.github.io/bmad-module-ultracode-goal/knowledge-graph-refresh/)** (`graphify_integration`) runs one [graphify](https://github.com/Graphify-Labs/graphify) rebuild as a run exits, and the invocation is pinned to `GRAPHIFY_NO_AUTO_REFRESH=1 timeout 300 graphify update .`, whose `update` subcommand re-extracts code and Markdown files locally with **no LLM call and no network request** (unless you turn on graphify's Google Workspace export with `GRAPHIFY_GOOGLE_WORKSPACE`). That is why it is that subcommand and not the general one: the general path sends changed documents, papers, and images to whichever LLM backend graphify auto-detects from your environment, on your API key, which is not something an unattended exit step should decide to do. The trade is that the refresh covers the parsed layer only: code, plus Markdown files that carry no LLM-derived layer yet. The `GRAPHIFY_NO_AUTO_REFRESH=1` assignment turns off the housekeeping graphify does outside `graphify-out/` before most commands: re-copying its own installed skill files (such as `~/.claude/skills/graphify/`) after a graphify upgrade, and replacing an outdated graphify OpenCode plugin, or dropping its stale `opencode.json` entry, under `.opencode/` in the project or your home directory, along with the lock files those leave under `~/.cache/graphify/skill-locks/`. So the refresh writes only `graphify-out/` (or wherever `GRAPHIFY_OUT` points).

[Cross-Session Recall](https://armelhbobdad.github.io/bmad-module-ultracode-goal/cross-session-recall/) (`cross_session_recall`) also ships **off** and is also advisory, but it no longer reaches a third-party tool. It used to read and write your past-run summaries through [claude-mem](https://github.com/thedotmack/claude-mem)'s MCP tools; it now keeps one summary per run in a store UCG owns, on this machine, under the folder `cross_session_recall_store` names. UCG reads and writes that store only through its two recall scripts, and invariant 7 keeps the model's own tool calls away from it while a run latch is present. During a run, recall is hook-latched and fails closed, and recalled content is sanitized and treated as data, never as instructions. The trust model, the redaction it does, and the redaction it explicitly does not guarantee are on that page. UCG does not use claude-mem any more, and it does not stop claude-mem's own capture where claude-mem is installed; while a run latch is present, invariant 6 keeps the run's tool calls away from claude-mem.

Neither graphify nor claude-mem is bundled, installed, or endorsed by this module, and neither is audited by it. Both are third-party software you install yourself, if at all; UCG calls graphify only when you ask it to, and does not call claude-mem at all.
