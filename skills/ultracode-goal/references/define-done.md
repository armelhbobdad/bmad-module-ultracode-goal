# Stage 3 — Define Done

Turn the Epic's acceptance criteria into **executable, red-phase acceptance tests** before any production code is written. The output of this stage is a per-story, machine-checkable Definition-of-Done: a generated `atdd-checklist` plus failing (`test.skip`) acceptance tests that Stage 4 will un-skip and drive to green. Run entirely in `{communication_language}`; TEA-produced documents are written in `{document_output_language}`.

This stage runs only after Stage 2 preflight returns green (intervention budget == 0). Preflight has already scaffolded the test framework (`bmad-testarch-framework`) and generated any missing acceptance criteria (`ucg-create-story`), so the framework is present and every in-scope story has *some* ACs by the time you arrive here. This stage hardens that into per-story executable tests.

## Per Epic — Test Design (once)

Run `bmad-testarch-test-design` in **Epic-Level Mode** for the Epic. This is the risk-and-priority backbone the rest of the run reads from. Its job here:

- **Risk matrix** — genuine risks (not features) with unique IDs, classified by category (TECH / SEC / PERF / DATA / BUS / OPS), each scored probability × impact (1–3 each); score ≥6 is high-priority and must carry a mitigation. This is what `bmad-testarch-trace` later resolves the gate against, so it must exist before Execute.
- **Priority classification P0–P3** — P0 = blocks core flow + high risk + no workaround. The gate Stage 5 reads (`gate_eval.py`) keys P0, P1, and overall thresholds to these priorities; those thresholds are hardcoded in TEA and TEA-owned. Do **not** restate or recompute the percentages; just ensure the test-design assigns the priorities honestly.
- **NFR thresholds** — for every NFR in scope, extract the concrete threshold from PRD / architecture / ADRs / epics / stories. Unknown thresholds are marked `UNKNOWN` and converted into a risk, assumption, or deferred item — **never guessed**. In production these feed `bmad-testarch-nfr` at the gate; a missing threshold that should have a value is a deferral candidate, not a fabrication.

Epic-Level Mode is selected by the presence of `sprint-status.yaml` (preflight reports `sprint_status_present`); if test-design prompts for system-vs-epic, choose **epic**. Force **Create** mode if it offers Resume/Validate/Edit — those are interactive and stall an unattended run.

**Test-design runs on any stack — do not skip it on a non-web module.** The framework fitness caveat in `references/preflight.md` is scoped to TEA's *browser generators*: ATDD in this stage, which on TEA 1.27.2 emits only Playwright/TypeScript scaffolds. Test-design is not one of them — it is risk-and-priority analysis over the planning corpus, and its output is a document, not a browser harness — and neither is trace, which runs on any stack too. So a `pytest` or `npm-test` module gets the same risk matrix and priorities a web module does. Reading the caveat as "the whole TEA chain is web-only" is what produces an empty test-design directory and leaves the ACs with no risk backbone to sharpen against; when ATDD's generator genuinely cannot serve the stack, the substitution is the hand-established red phase in gate.md's non-web section, and hand-authored trace artifacts only where trace itself cannot run; never a skipped test-design.

A `CONCERNS`-grade gap in the test plan (e.g. an `UNKNOWN` NFR threshold that does not block any P0 story) appends to `{workflow.deferred_work_path}` and the Epic keeps moving. A genuine red gap — no risk coverage for a P0 flow — is not deferrable; resolve it before proceeding to per-story work.

## Per Story — Create then ATDD

For every **in-scope** story, in sprint order (leave out a parent that preflight step 2 set `done` as a container):

1. **`ucg-create-story`**: produce the dedicated story file with full implementation context and *clear, testable* acceptance criteria. If preflight already generated this story, treat the change request as a refinement, not a re-create. Vague ACs are the single most common cause of the next step halting, so sharpen them here.

   **A decomposed child gets no story file.** Skip this step for a key the readiness check listed in `checks.decomposed_children` when the split is recorded (its split record (`.split-<parent key>.json` beside `sprint-status.yaml`, which `scripts/story_sizing.py --record` writes) names the child, the child's row cites the parent ACs it claims, or `.decision-log.md` names the parent and the ACs each child claims): the child has no story file and must never get one, and its criteria are the parent ACs it claims, in the parent's file (`references/execute.md`, step 1). A listed key with none of these records is a story of its own that reads like a child (above a `done` parent's row, or under a parent whose row was removed): create its file here, and log in `.decision-log.md` that the readiness check never read its criteria. One such key already has its file: a key whose title starts with a single letter or a roman numeral (`2-4-a-new-login-page`) reads one level below its story number, so its own story file named by that number alone (`2-4.md`) or by another title is listed as the parent of a removed row. When the listed parent file is that story's own (`parent_row` is `null`, no other key in the list names the same file, and the file's title and criteria are this key's), rename that file to `<key>.md` instead, in one `mv <that file> <its folder>/<key>.md` call (a filesystem command `acceptEdits` runs without asking on a path inside the project, unlike a git move, which no allow rule covers), then run this step on it as a refinement, and log the rename: the readiness check did read its criteria. A file two listed keys name is a parent's, so rename it for neither.

   On a project whose artifact tree git does not track (preflight's `impl_artifacts_tracked: false`), no acceptance criterion may have a test read a file under that tree at run time: it does not exist in CI. Preflight step 2 states the rule ("A gitignored artifact tree").

2. **`bmad-testarch-atdd`** — generate the red-phase acceptance test scaffolds for that story. This writes:
   - `atdd-checklist-{story_key}.md` under the TEA test-artifacts directory — the per-story checklist mapping each AC to its planned test(s).
   - The acceptance test files themselves, **every test marked `test.skip()`** (TDD red phase). ATDD verifies this and errors if any generated test is not skipped — that is correct and expected; the tests are *supposed* to fail/skip until Stage 4 implements the feature and un-skips them.

   `bmad-testarch-atdd` **HARD HALTS** if the story lacks clear acceptance criteria or the framework is not configured. Both are preconditions this stage's step 1 and Stage 2 preflight exist to satisfy, so if atdd halts anyway, the story's ACs are still too vague: loop back to `ucg-create-story` for that story and re-run atdd. Do not hand a story to Execute with a halted or absent atdd-checklist. **One halt is not a vague-ACs halt and no re-loop fixes it: a stack ATDD's browser generator cannot run on at all** (the framework-fitness caveat above). There the checklist is structurally unproducible, and its production substitution is defined in `references/gate.md`'s non-web section: the red phase is established BY HAND in the stack's own harness, authored, RUN and captured before the story's first implementation edit (`references/execute.md` step 1 restates it at the point of action). *That substitution* is what such a story hands to Execute; record it per story in `.decision-log.md`, and never loop it back through a generator that cannot run.

   **For a decomposed child, run it under the child's own key** (on a stack ATDD cannot run on, the hand-established red phase above stands in, as for any story, scoped to the parent ACs the child claims). Give it the parent's story file for the text of the parent ACs the child claims, and have it write `atdd-checklist-<child key>.md` with the child's key as its story key and the parent's key and those AC numbers in its frontmatter. ATDD otherwise takes the story key from the file it reads, so it would write the parent's checklist, and each sibling's into the same file, while Execute and its commit guard read the child's. Build its criterion registry from the parent's whole AC list, so each id keeps the parent's number, and scaffold the claimed ids only. Treat the parent's file as one ATDD cannot update safely, so it skips the link back into it: the parent's story file is never edited. ATDD's closing checks that every declared criterion has a scaffold and that the link back was written do not apply to a child, and are not gaps to fix. A halt on vague criteria is no loop back here: never run `ucg-create-story` for the child and never edit the parent's file. Record the halt in `.decision-log.md` and escalate as Execute's sub-skill halt catch-all does (`references/execute.md`: write the typed escalation sidecar, then stop), naming the parent ACs that need sharpening.

   Force **Create** mode (not Resume/Validate/Edit) for the same unattended reason.

**In `--light`:** run step 1 (`ucg-create-story`) but **skip step 2 (`bmad-testarch-atdd`)**: `--light` produces no executable red-phase acceptance tests. The story file and its acceptance criteria become the Definition-of-Done and the oracle `bmad-testarch-trace` resolves the Stage 5 gate against, mirroring gate.md's `--light` branch (which runs only `bmad-testarch-trace`). The per-Epic test-design above still runs in `--light`: `bmad-testarch-trace` consumes its risk scores and P0–P3 priorities when they are available, and they are the backbone you sharpen the ACs against in either profile. Sharpen the ACs here exactly as you would for production: under `--light` they are the *only* machine-checkable DoD a story gets, so vague ACs leave the trace gate nothing to resolve against.

Under `--light`, a decomposed child still gets no story file at step 1: its oracle is the parent ACs it claims, in the parent's story file.

**A delegated skill that is not installed.** If a skill this stage delegates to is not installed (the Skill tool does not know its name; for example `ucg-create-story`, which UCG's installer copies beside the ultracode-goal skill and a partial or older UCG install lacks), do not substitute another skill (`bmad-build`, `bmad-build-auto`, or BMAD's deprecated `bmad-create-story` and `bmad-dev-story`) and do not write the story file or its tests by hand: Stage 4 and the gate read the artifacts these skills produce, and a stand-in reaches them looking like the real thing. Escalate as Execute's sub-skill halt catch-all does (`references/execute.md`: write the typed escalation sidecar, then stop), for the story concerned or, when the per-Epic test-design is the missing skill, for the Epic's first in-scope story. Name the cause in `decision_needed`: Stage 2's `story_skills` blocker refuses a launch without `ucg-create-story`, so a missing `ucg-create-story` here means the install changed after preflight ran. Its `tea_skills` blocker likewise refuses a launch without the TEA skills the run's profile delegates to, so a missing one here also means the install changed after preflight ran.

## Exit condition (testable)

Stage 3 is complete, and Stage 4 may begin, when **all three** hold:

- The Epic has a `bmad-testarch-test-design` plan with a populated risk matrix, P0–P3 priorities assigned, and every in-scope NFR threshold either resolved or explicitly marked `UNKNOWN`/deferred.
- **Every in-scope story** has a story file with clear acceptance criteria. A recorded decomposed child, which has none of its own, meets this through its parent's story file, which holds the parent ACs it claims.
- **Every in-scope story** has a generated `atdd-checklist-{story_key}.md` and red-phase (`test.skip`) acceptance tests on disk — **production only**, on a stack ATDD can run on. Under `--light` this is skipped by design; the story file's acceptance criteria stand as the trace oracle instead, and this bullet is satisfied by the clear-ACs bullet above. On a **non-web stack** (ATDD's generator cannot run), this bullet is satisfied by the recorded hand-establishment commitment per story — the substitution in step 2 above — never by a checklist nobody could generate.

In production, if any in-scope story is missing its atdd-checklist, this stage is not done — Execute has nothing executable to drive that story to. (Under `--light` an absent atdd-checklist is expected, not a gap; on a non-web stack the hand-established red phase per `references/gate.md`'s non-web section stands in for it, and the decision log says so per story.) Record in `.decision-log.md`: the test-design verdict, each story's AC + checklist status (or the `--light` skip), and any deferral appended to `{workflow.deferred_work_path}`.
